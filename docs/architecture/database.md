# 数据库架构

## 决策

服务端支持 SQLite 和 PostgreSQL 两种正式部署模式。一次部署只连接一种数据库；`DATABASE_URL` 决定数据库类型和连接位置。SQLite 与 PostgreSQL 之间不迁移数据，切换数据库意味着创建新的部署和新的空库。

服务端采用 SeaORM 管理连接、实体映射和事务。SeaORM 是存储基础设施，不进入路由、协议桥接和领域模型。

## 适用边界

SQLite 用于单进程、轻量部署。数据库文件随该服务实例部署和备份。

PostgreSQL 用于正式生产、多实例运行和由运维体系管理的数据库服务。连接、备份、可用性和访问控制由部署环境负责。

两种模式对外提供相同的管理 API 与 `/v1` 协议行为。身份隔离、供应商密钥加密、接入点模型解析、请求记录和统计口径不得因数据库类型改变。

## 分层

```text
路由、协议桥接、后台任务
        ↓
Storage 领域操作
        ↓
SeaORM 连接、实体与事务
        ↓
SQLite 或 PostgreSQL
```

`Storage` 是服务端唯一的持久化入口。它以业务操作表达职责，例如注册身份、原子保存供应商及模型、保存接入点映射、解析候选供应商、写入会话和查询统计。

`AppState` 只持有 `Storage`，不暴露 `DatabaseConnection`、连接池或实体。路由、协议桥接和观测模块不得绕过 `Storage` 直接访问数据库。

不引入通用 `CrudRepository<T>`。Provider、接入点、身份和统计的约束不同，泛型 CRUD 会掩盖事务边界、身份范围和引用校验。SeaORM 实体只用于存储映射，不直接作为 API DTO 或领域对象返回。

## 数据模型

现有业务事实继续由以下资源表达：

- 身份及设备凭据摘要。
- 供应商、加密后的 API Key 与供应商模型。
- 接入点、接入点模型映射与最近成功候选供应商。
- Responses 会话、请求记录和统计所需元数据。
- 身份范围内的模型别名。

资源 ID 继续使用 UUID 字符串，避免让自增主键语义进入 API。时间在领域层统一使用 UTC；DTO 按既有格式序列化。结构化元数据使用 JSON 值，业务查询不得依赖 SQLite 专属 JSON 函数。密文、凭据哈希和令牌保持不透明字符串，不作为 ORM 关系或 JSON 字段处理。

实体关系、唯一约束、外键和索引由统一 schema 初始化模块定义。全新空库首次启动时创建完整当前 schema；已有完整 schema 不执行 DDL；仅存在部分业务表时拒绝启动，要求创建新的部署。每一项跨资源写入仍须由单个事务完成；失败时不得留下部分供应商、空接入点或失配的模型映射。

## 连接与启动

`DATABASE_URL` 是唯一数据库选择来源：

```text
sqlite:data/relay.db?mode=rwc
postgres://<user>:<password>@<host>:5432/<database>
```

服务根据 URL scheme 创建 SQLite 或 PostgreSQL 连接。缺失、未知 scheme、无法连接或数据库版本不满足要求时启动失败，不回退到其他数据库或隐式创建本地 SQLite 文件。

连接池容量通过一个明确的服务端配置项控制；SQLite 保持单进程写入模型，PostgreSQL 按部署实例配置连接数。主密钥、监听地址和上游策略保持现有独立配置，不从数据库配置推导。

## 初始化与发布

数据库 schema 不采用版本化迁移，也不提供独立 DDL 命令或部署 Job。

- 每次 SQLite 或 PostgreSQL 部署必须使用全新空库。
- 服务启动时只为全新空库创建当前完整 schema。
- 已有数据库不进行升级、修复或结构兼容；部分 schema 直接拒绝启动。
- schema 变化意味着目标数据库需要新部署和新空库，原部署数据由其自身保留或备份。
- SQLite 与 PostgreSQL 的差异只允许留在统一 schema 初始化或明确的数据库方言适配模块中，不能散落在领域操作中。

## 查询规则

常规读取、写入、关联和事务优先使用 SeaORM 的跨数据库能力。需要聚合、候选排序或批量查询时，可使用 SeaORM 的查询构造器。

只有无法由跨数据库查询表达的需求，才能增加方言适配。适配必须位于存储基础设施中，以同一领域方法暴露结果，并在 SQLite 与 PostgreSQL 上分别有测试。禁止在路由或协议转换逻辑中拼接 SQL，也禁止使用 `PRAGMA`、`sqlite_master` 或 PostgreSQL 专有语法判断业务状态。

## 验证矩阵

每个数据库支持版本至少覆盖以下事实：

- 全新数据库可以初始化完整 schema 并启动服务。
- 身份、供应商、接入点、模型映射、会话和请求记录具有相同的约束与可见范围。
- 供应商及模型、接入点及映射的完整保存保持事务原子性。
- 设备凭据轮换、接入点令牌认证、候选供应商解析和失活身份清理保持既有语义。
- 请求记录、时间范围和统计聚合在两个数据库中返回一致结果。
- 重复资源、跨身份访问、无效引用和数据库约束失败均返回既有稳定错误码，且不泄露数据库细节。

本地开发可以默认运行 SQLite 契约测试。SQLite 测试通过不证明 PostgreSQL 部署可用；发布 PostgreSQL 部署前仍须在全新空 PostgreSQL 数据库上验证 schema 初始化和实际读写。

## 排除项

本架构不包含跨数据库迁移、版本化 schema 升级、双写同步、读写分离、分库分表、数据库租户隔离、ORM 自动同步 schema 或运行时切换数据库。后续若出现独立需求，应在不破坏 `Storage` 领域边界的前提下另行设计。
