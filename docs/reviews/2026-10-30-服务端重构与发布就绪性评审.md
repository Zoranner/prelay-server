# Prelay 服务端重构与发布就绪性工程评审报告

## 评审范围

本次只评审 `prelay-server` 当前 checkout 的工程体系、分层结构、存储实现和发布就绪性，不评价功能需求完成度，也不把真实上游、桌面端和部署环境的联调结果混入代码结论。

评审对象是 `v0.4.2..HEAD` 的 16 个提交，当前 HEAD 为 `141fff7`。这段范围同时包含：

- 七个依赖层的目录重构和结构门禁。
- 按会话线程保存活动正文、去重、窗口切换和数据库迁移。
- 供应商声明上游请求头、新增 OpenCode Go 供应商。
- 流式首块测试稳定化和供应商目录测试拆分。

`prelay-client`、`prelay-protocol` 只核对 submodule 指针和发布依赖，不评审其运行时代码。

## 评审依据

- 工作区 `AGENTS.md`：三个子仓独立提交；协议契约先改 `prelay-protocol`；发布、推送和打标签分别授权。
- `prelay-server/AGENTS.md`：只改当前 checkout；Rust 修改执行 fmt、严格 Clippy、测试和 `git diff --check`；真实部署与自动化测试分开表述。

- 当前仓库文件、Git 状态、远端 tag/Release 和实际命令输出。

## 总体结论

结构重构的主体已经落地。`src/` 顶层只剩 `bootstrap`、`inbound`、`service`、`codec`、`outbound`、`store`、`domain` 七个目录，根目录只剩 `main.rs`、`lib.rs`、`error.rs`；`src/` 共 28,951 行，单文件最大 407 行；格式、严格 Clippy、全量测试和 release 构建都通过。就“这次目录重构本身是否可维护”而言，方向是成立的，`tests/source_layout` 的 8 项门禁也能执行。

当前 HEAD 不能直接作为新版本发布。发布前至少要处理三件事：

- 线程 JSONL 末尾半行没有恢复路径。一次进程崩溃或写入中断会让该会话后续请求持续返回 500，启动诊断还只扫描已经不再生成的 `.part` 文件。
- `Cargo.toml`、Compose 和 README 仍是 `0.4.2`，而 `v0.4.2` 已经发布。按现有 release workflow，新 tag 必须与 `Cargo.toml` 完全一致，不能复用已发布的 `v0.4.2`。
- README 仍写“按活动一份文件、`.part`、原子重命名”，实际已经改为“每个身份每个线程一份追加文件”。升级说明也没有覆盖新的 `activity_rollout_v2` 迁移。

另有四项中风险建议在发布前或发布后尽快收口：`domain` 反向依赖 `codec` 且门禁主动放行；流式终结阶段吞掉正文追加错误后仍记录 `completed`；线程文件每次请求全量同步读取和解析；`identity_response_sessions` 仍保存完整未脱敏输入输出，与 README 的数据库边界表述冲突。

在这些问题中，前两项属于明确的发布阻断；第三项属于升级操作风险；其余可以作为发布后的结构治理项，但需要明确取舍。

以上是评审时（`141fff7`）的结论。按 `0.4.3` 收口后的结果见“整改后状态”。

### Responses 状态协议整改

- 响应 ID：`/v1/responses` 的响应（含流式）统一使用 Prelay 生成的 `resp_` ID；上游 ID 只保存到 `upstream_response_id`。流式只改写 `response.id` 和顶层 `response_id`，保留 `item.id`、`item_id`、`call_id`。

### 性能边界

持久索引关闭了“进程重启后首次访问必须全量读取”的缺口。首次访问仍没有索引的旧线程、或索引失效时，必须完整读取并解析一次以重建索引；热读仍按本次请求携带的历史事件计算 O(n) 前缀哈希，这是协议输入校验成本，不再读取完整线程文件。

手动基准（20,000 个事件、2.78 MB，release 构建）：cold 172.2 ms，indexed 113.9 ms，warm 106.5 ms。cold 是删除索引后的全量读取，indexed 是新进程从持久索引命中，warm 是同一进程内复用缓存。

## 主要问题

### 线程 JSONL 半行没有恢复路径，单线程会持续失败

问题定性：违反项目已确认的生命周期和恢复要求，高风险，发布阻断。

证据：

- `RolloutStore::begin` 在追加前读取整个线程文件；文件不以换行结束时直接返回 `PartialLine`，没有截断、降级或新分段路径，见 `src/store/rollout/mod.rs:107-143`。
- `recover_interrupted` 只把数据库中的 `writing` 记录改成 `partial`，不修复文件，见 `src/service/activity.rs:40-48`。
- 启动诊断 `warn_incomplete_rollout_files` 只调用 `part_files()`，而 `part_files()` 只扫描 `.part` 文件，见 `src/bootstrap/diagnostics.rs:23-37` 和 `src/store/rollout/scan.rs:10-38`。
- 新的 `begin` 直接对最终 `.jsonl` 使用追加模式，没有 `.part` 中间文件，见 `src/store/rollout/mod.rs:147-170`。`src/store/rollout/tests.rs:139-155` 仍在构造 `.part` 文件，覆盖的是已经不再生成的路径。
- 现有线程测试只覆盖正常追加、窗口切换和行号区间，见 `src/store/rollout/thread_tests.rs`；没有覆盖“最后一行只写了一半后再次请求”的场景。

风险：

- 进程在 `write_all` 和 `flush` 之间崩溃、磁盘写满或文件被截断时，线程文件可能留下没有换行的半行。
- 该线程的后续请求都会在活动记录入口返回 `RolloutError::PartialLine`（流式入口是 `begin_stream`，非流式入口是 `record_completed`），经 `StorageError::Rollout` 映射为 `internal`，客户端持续收到 500。Codex 会复用同一个 thread id，因此这不是一次性失败，而是整段会话不可用。
- 旧方案使用 `.part` 加原子重命名，崩溃最多留下未完成临时文件，不会污染后续可追加的最终文件；新方案把最终文件变成可持久污染的状态，这是行为回退。
- 运维目前既看不到告警，也没有修复命令；只能人工找到文件并从末尾截断。

建议：

1. 在 `begin` 或启动恢复阶段检测末尾半行，校验有效前缀后截断到最后一个完整换行，并记录可定位的 thread id 和丢弃字节数。
2. 如果不接受截断，改为写入新的段文件或新的 thread 文件，并更新活动索引，保证原文件不再阻塞后续请求。
3. 启动扫描改为检查 `.jsonl` 尾部，而不是只检查已经不再生成的 `.part`；同时为半行恢复、磁盘满和解析失败补测试。
4. 为这类错误使用稳定错误码并在日志中给出修复路径，不要只返回通用 `internal`。

### domain 反向依赖 codec，结构门禁主动放行

问题定性：违反项目已确认的分层规范，中风险。

证据：

- 设计明确写“`domain` 只依赖 `error` 和外部 crate”，见 `docs/superpowers/specs/2026-10-30-server-structure-design.md:155`。
- `tests/source_layout/dependencies.rs:38` 把 `domain` 的允许依赖写成 `["domain", "codec"]`，等于允许 `domain` 引用上层。
- `src/domain/activity/events.rs:1-8` 直接引用 `crate::codec::bridge::stream::StreamStatsSnapshot` 和 `crate::codec::internal::{...}`；`src/domain/activity/event_values.rs:3` 引用 `crate::codec::internal::InternalContentPart`。

风险：

- `domain` 不再是依赖图最底层，`codec` 反而被 `domain` 需要；这会让“依赖只允许自上而下”的说明失去实际约束力。
- 门禁测试通过，但它验证的是被放宽后的规则，不是设计文档里的规则。后续开发者会继续把编解码类型放进领域事件，结构会再次漂移。

建议：

- 把 `StreamStatsSnapshot`、`InternalMessage`、`InternalContentPart` 等协议中立的内存模型下沉到 `domain`，或者把活动事件构造移到 `codec`/`service`，让 `domain` 只保留自己的类型。
- 删除 `allowed_layers("domain")` 中的 `codec` 例外，并增加一个会因 `crate::codec` 引用而失败的回归测试。

### 流式终结吞掉正文追加错误后仍记录完成

问题定性：违反活动正文完整性契约，中风险。

证据：

- `src/service/recording/state.rs:375-395` 在终结时逐条追加最终事件；每条失败只调用 `log_stream_storage_failure("append-rollout", ...)`，然后继续。
- 随后 `finish_with` 只要 flush 成功就返回 summary，`complete_stream` 会把活动索引写成 `completed`；summary 的字节数和 hash 只覆盖已经写成功的部分。

风险：

- 磁盘写满、文件被截断或事件序列化失败时，活动可能被标记为 `completed`，但正文缺少最后一段响应、用量或错误事件。
- 后续把活动文件作为审计或记忆来源时，`completed` 不能证明正文完整；数据库中的 hash 也只能证明已写入部分。

建议：

- 终结阶段任何正文追加失败都应把活动标为 `partial` 或 `failed`，不要继续写 `completed`。
- 如果选择 best-effort，应在索引中记录 `last_error` 和明确的降级状态，并在 README 中说明 `completed` 的含义。

### 线程文件每次请求全量同步读取和解析

问题定性：建议优化，性能和资源风险，中风险。

证据：

- `RolloutStore::begin` 虽然是 `async fn`，但内部直接使用 `fs::create_dir_all`、`fs::read_to_string` 和 `OpenOptions`，见 `src/store/rollout/mod.rs:129-170`。
- 每次请求都会把整个线程文件读入内存、用 `parse_events` 解析全部事件，再用 `common_prefix_len` 做全量前缀比较；这些工作发生在持有线程锁期间。
- `locks` 是一个只增不减的 `HashMap<PathBuf, Arc<AsyncMutex<()>>>`，见 `src/store/rollout/mod.rs:107-175`。
- 活动正文不设应用层大小上限，也不自动归档，这是已确认的产品边界；因此线程文件会随对话历史持续增长。

风险：

- 长会话的每次请求都会阻塞一个 Tokio worker，延迟和内存占用随文件大小线性增长。
- 同一线程的并发请求会排在整段流式活动之后，最坏情况下等待时间等于上一次上游流的完整时长。
- 锁表随线程数量增长，长期运行会积累不可回收的条目。

建议：

- 把文件读取、解析和截断放进 `spawn_blocking`，至少不要把同步 I/O 放在持有异步锁的 executor 线程上。
- 维护文件尾部偏移或索引，避免每次请求全量解析；如果暂时不优化，先用长线程基准测试量化延迟和内存峰值。
- 在线程活动结束后回收锁表条目，或使用有上限的锁表。

### identity_response_sessions 仍保存完整未脱敏输入输出

问题定性：违反项目已确认的安全边界，文档与实际不一致，中高风险，前次评审遗留。

证据：

- `src/store/storage/sessions.rs:67-68` 把 `input_messages` 和 `response.output` 直接序列化到 `identity_response_sessions.input_messages_json` 和 `output_items_json`；`src/store/entity/identity/response_sessions.rs:5-17` 确认这两个字段是完整 JSON。
- `README.md:108` 在描述活动正文时写“数据库只保存索引、状态、大小和 hash”，容易被理解为数据库不保存正文；但协议续接表仍保存完整输入和输出。
- `prelay-server/AGENTS.md:11` 要求请求统计不默认保存完整 prompt 或响应正文；这条规则针对统计表，但当前 README 没有把 response session 的例外说清楚。
- `docs/reviews/2026-10-23-当前工作树与活动存储评审.md` 已把该项列为“仍未关闭”，本次重构没有改变这条存储路径。

风险：

- prompt、工具结果和内联图片可能原样进入 PostgreSQL 和数据库备份，绕过活动 JSONL 的脱敏边界。
- 部署方按 README 的“数据库只保存索引”理解备份敏感级别，会低估数据库和备份的敏感数据范围。

建议：

- 二选一：把 response session 缩小为协议续接所需的最小状态；或者明确承认它是第二个正文副本，并定义脱敏、保留、备份和访问规则。
- 如果保留完整正文，至少修正 README 和数据库文档，说明 `identity_response_sessions` 含完整输入输出，备份必须按敏感数据处理。

### 其他低风险问题

- `src/lib.rs:40-168` 仍把 `test_support` 内联在库根，且是无条件 `pub mod`。设计文档 `docs/superpowers/specs/2026-10-30-server-structure-design.md:39,112,173` 要求移到 `bootstrap/test_support.rs`，根级 `lib.rs` 只保留声明、`AppState` 和导出。当前结构门禁没有检查这一点，生产库也暴露测试数据库辅助函数。
- `src/lib.rs:35` 在代理客户端构造失败时把完整 `proxy_url` 放进 `AppError::Upstream` 消息；`src/domain/catalog/validation.rs:316-334` 只校验 http/https，不拒绝 userinfo；`src/error.rs:37-39` 会把该消息返回给调用方。如果代理地址写成 `http://user:pass@host:port`，错误路径可能把代理凭据暴露给持有 Endpoint Token 的调用方。建议错误消息只保留 scheme/host/port，或禁止目录代理地址携带凭据。

## 整改优先级建议

### 发布前必须完成

- 为线程 JSONL 末尾半行增加恢复或降级路径，并把启动扫描从 `.part` 改为 `.jsonl` 尾部；补半行、磁盘满和解析失败测试。
- 把版本提升到 `0.5.0` 或 `0.4.3`，同步 `Cargo.toml`、`Cargo.lock`、Compose 和 README 的镜像标签。
- 更新 README、数据库文档和 Release 说明，写清楚线程文件布局、`activity_rollout_v2` 迁移、旧文件保留和备份要求。
- 明确 `identity_response_sessions` 的正文边界；如果继续保持完整正文，先修正 README 和备份说明。

### 发布后尽快完成

- 修正 `domain -> codec` 反向依赖，删除结构门禁中的 `codec` 例外。
- 让终结阶段的正文追加失败进入 `partial`/`failed` 状态，不要继续记录 `completed`。
- 把线程文件的读取、解析和截断移出 async executor，并用长会话基准测试验证延迟和内存。

### 可以随后处理

- 把 `test_support` 移到 `bootstrap/test_support.rs`，并按独立任务决定是否加 `cfg(test)`。
- 清理代理 URL 错误消息中的凭据，补充安全回归测试。
- 删除已经不再生成的 `.part` 扫描和对应测试（已关闭）。

## 结论边界

本次结论覆盖当前 checkout 的静态结构、Rust 门禁、临时 PostgreSQL 上的全量测试和 release 构建，不覆盖 Docker 镜像、GitHub Actions、真实部署库和真实上游。修复上述发布前事项后，可以再按 `prelay-server` 的 release workflow 做一次远端发布核验；本次没有执行推送、打标签或发布。
