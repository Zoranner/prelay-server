# Prelay Server Rust 工程评审报告

## 评审范围

本次只评审活动正文生命周期修复的工程实现、状态模型、异步生命周期、数据库迁移、测试和验证边界，不评价其他 provider/model catalog 改动，也不评价业务功能完成度。

## 评审依据

- 当前服务端 `AGENTS.md`：以当前 checkout、实际数据库和验证结果为准；不覆盖用户已有未提交改动。
- Rust 工程评审基线：检查 async 取消、后台任务、事务、迁移、错误处理、格式、Clippy、测试和构建。
- 当前实现文件：`src/observability/stream_stats/state.rs`、`src/storage/activity_contents.rs`、`src/storage/recordings.rs`、`src/schema/activity_content.rs`、`src/schema/mod.rs`、`src/main.rs`。
- 当前数据库只读核验：PostgreSQL `prelay` 数据库，历史活动正文状态和活动-正文关联统计。

## 总体结论

本次实现已经覆盖正常 EOF、上游流错误、空流、客户端提前释放、历史状态迁移和运行期回收。复评确认并修正了活动状态模型：流式活动使用 `streaming` 表示进行中，只有终止事件才进入 `success` 或失败终态；回收逻辑不再把活跃流当作已完成请求。

当前代码可以进入发布前验证阶段。仍需在真实 PostgreSQL 和部署环境验证迁移、并发启动及真实 HTTP 客户端断开行为。

## 主要问题

### 流式活动的 `success` 状态被错误当作终态（已修复）

问题定性：违反状态模型一致性要求，高风险；本轮已修复。

证据：

- [src/routes/v1/responses/native.rs](../../src/routes/v1/responses/native.rs) 等流式入口在创建 `ActivityInsert` 时直接设置 `status: "success"`，此时上游流尚未结束。
- [src/observability/stream_stats/state.rs](../../src/observability/stream_stats/state.rs) 在流开始阶段把该活动写入数据库，并只在错误时改成 `failed`；正常流的 `success` 是初始值，不是终止事件。
- [src/storage/activity_contents.rs](../../src/storage/activity_contents.rs) 的运行期回收按父活动 `status IN ('success', 'failed')` 筛选长期 `capturing` 正文。
- [src/main.rs](../../src/main.rs) 每五分钟执行一次回收。

原风险：

- 一个正常运行超过五分钟的流，其正文可能在仍处于捕获过程中被改为 `pending`。
- 下游正文处理可能在输出尚未完整时读取内容。
- 回收后流仍可能继续写入同一正文，造成“已进入待处理状态但仍被更新”的竞态。
- 现有测试把“活动状态为 `capturing`”作为活动中的夹具，但生产代码实际使用的是 `success`，没有覆盖真实状态。

本轮处理：

- 流式活动开始时统一写入 `streaming`。
- `record_final_usage` 只更新统计字段，不覆盖活动状态。
- 只有 EOF 才写入 `success`；上游错误和下游断开写入失败状态。
- 回收条件只匹配父活动 `success` 或 `failed`。
- 新增测试验证 EOF 前活动保持 `streaming`。

### 正文终态时间字段没有写入（已修复）

问题定性：规范缺失导致的可观测性风险，中风险；本轮已修复。

证据：

- `activity_contents` 表包含 `completed_at` 字段。
- 正常收尾、错误收尾和自动回收只更新 `status`、`updated_at` 及租约字段，没有设置 `completed_at`。
- 当前代码没有读取该字段，因此暂时没有直接业务错误，但数据库无法区分“正文刚刚写入”和“正文已完成很久”。

原风险：

- 后续正文处理、审计或运维无法使用 `completed_at` 判断真实完成时间。
- `updated_at` 同时承担内容修改时间和状态迁移时间，语义不够明确。

本轮处理：

- 正文进入 `pending` 时写入 `completed_at`。
- 自动回收同时写入完成时间并清除租约字段。
- 测试已验证终态正文保留原内容并产生完成时间。

### PostgreSQL 迁移和多实例启动缺少真实验证（保留）

问题定性：验证覆盖不足，中风险。

证据：

- `src/schema/activity_content.rs` 为 PostgreSQL 和 SQLite 分别生成不同 SQL。
- 当前自动化迁移测试只使用 SQLite。
- 迁移已改为先使用数据库原子插入抢占版本；未抢占到版本的实例直接跳过，因此原先的查询后插入竞争已消除。

风险：

- 真实 PostgreSQL 的时间转换、`CURRENT_TIMESTAMP::text` 和更新语义尚未通过实际迁移验证。
- 多实例并发启动尚未在真实 PostgreSQL 中验收。

建议：

- 在隔离的 PostgreSQL 测试数据库上执行迁移测试，覆盖真实旧数据。
- 在隔离 PostgreSQL 数据库上执行真实迁移和并发启动验收。

### 第一优先级：已完成活动和正文的终态契约修正

- 已有测试证明运行期回收只处理终态活动。

- 正文终态转换已写入 `completed_at`。
- 仍需在隔离 PostgreSQL 数据库中验证启动迁移和重复启动。
- 仍需在真实多实例条件下验证迁移版本竞争不会导致服务启动失败。

### 第三优先级：部署后真实验收

- 发布新服务端并重启临时环境。
- 观察 `capturing` 是否只存在于活跃流。
- 观察 `capturing` 是否持续增长。
- 对照迁移版本和正文状态统计确认历史记录已自动收敛。
