# Prelay Server Rust 工程评审报告

## 评审范围

本次评审覆盖当前 `master` 服务端的 Rust 模块边界、测试组织、依赖与仓库治理、质量门禁和可维护性。不评价具体业务需求是否正确。

用户明确要求将任意生产源码或测试脚本的物理行数限制在 450 行以内；超过该阈值直接视为需要重构的严重结构问题。本报告按该要求评估。

## 评审依据

- 仓库 `AGENTS.md` 的 Rust 模块、验证和安全边界。
- Rust 工程评审基线中的 crate 边界、异步职责、测试组织和质量门禁要求。
- 当前 `Cargo.toml`、`src/`、`tests/`、Git 工作树及质量门禁结果。

## 总体结论

当前服务具备可构建和可测试性，但不满足 450 行结构门槛：15 个生产源码文件与 2 个集成测试文件超过上限。最大路由文件达到 1990 行，且在内联测试开始前仍有 752 行生产逻辑，已经同时承载路由、候选执行、协议桥接、会话、日志和夹具职责。

因此当前工程应先完成结构重构，再继续在这些文件上叠加功能。质量门禁通过不能抵消该结构问题。

## 检查情况

- `cargo fmt --all -- --check`：通过。
- `cargo clippy --all-targets --all-features -- -D warnings`：通过。
- `cargo test --all-targets --all-features`：通过，无失败、无 ignored 用例。
- `cargo tree -d`：存在的多版本加密与随机数依赖均由 SeaORM/SQLx 依赖链引入，未发现服务代码直接引入第二套平行 HTTP、日志或异步运行时。
- `unsafe` 只出现在 `tests/database_configuration.rs` 的环境变量测试辅助代码中；生产源码未发现 `unsafe`。

## 主要问题

### 生产源码普遍超过 450 行

**定性：违反用户确认的硬性结构约束，严重，必须重构。**

以下生产文件超过阈值：

| 文件 | 行数 | 首个内联测试前的生产行数 |
| --- | ---: | ---: |
| `src/routes/v1/responses.rs` | 1990 | 752 |
| `src/routes/v1/messages.rs` | 1799 | 654 |
| `src/routes/v1/images.rs` | 1321 | 350 |
| `src/routes/v1/chat.rs` | 1002 | 272 |
| `src/storage/stats.rs` | 809 | 562 |
| `src/providers/spec.rs` | 799 | 394 |
| `src/providers/chat_completions.rs` | 772 | 395 |
| `src/schema.rs` | 665 | 509 |
| `src/bridge/responses_decode.rs` | 656 | 366 |
| `src/observability/stream_stats.rs` | 627 | 326 |
| `src/storage/mod.rs` | 627 | 627 |
| `src/bridge/anthropic_decode.rs` | 596 | 322 |
| `src/bridge/stream/encode_anthropic.rs` | 511 | 431 |
| `src/bridge/stream/decode_anthropic.rs` | 516 | 359 |
| `src/bridge/stream/decode_responses.rs` | 484 | 333 |

`responses.rs` 和 `messages.rs` 的生产区混合了公开 handler、候选循环、上游请求、三种协议桥接、会话历史、请求日志和流式记录。`storage/mod.rs` 公开了 40 余个跨身份、Provider、Endpoint、会话、日志和统计方法，成为无边界门面。`schema.rs` 在一个文件中维护九张表及其索引和初始化策略。

这些文件的共同变化范围过大，任何协议、日志或持久化变动都会扩大评审和回归面；继续在原文件新增分支会直接违反既定行数约束。

建议按职责而不是按固定行数机械切片：

- 将 `routes/v1/responses.rs` 和 `messages.rs` 拆成入口与鉴权、候选执行、协议专属桥接、会话/日志、测试五类模块；不要为了去重强行合并 OpenAI 与 Anthropic 的协议语义。
- 将 `images.rs`、`chat.rs`、`providers/spec.rs`、桥接 decoder 和流统计的内联测试移为同级测试模块，保证生产文件和测试文件都独立低于阈值。
- 将 `Storage` 的公开实现按身份、Provider、Endpoint、协议访问、会话、请求日志和统计移入对应子模块；`storage/mod.rs` 只保留类型、错误和子模块声明。
- 将 schema 的表定义、索引和初始化编排分离；初始化入口保留在 `schema.rs`，具体表结构按领域拆分。

### 集成测试按资源领域混装并超过阈值

**定性：违反用户确认的硬性结构约束，严重，必须重构。**

`tests/management_isolation.rs` 为 1133 行，混合身份凭据、Provider、Endpoint、统计、模型去重、Ping、模型发现和上游失败行为。`tests/identity_storage.rs` 为 495 行，混合凭据加密、事务、候选排序、会话、环境变量和 fixture。

这使失败定位依赖大量共享准备代码，且一次管理 API 变更会触发跨领域测试文件冲突。

建议把前者按 `management_identity`、`management_providers`、`management_endpoints`、`management_stats`、`management_provider_operations` 拆分，把后者按身份凭据、Provider/Endpoint 写入、协议候选与会话拆分；共享 HTTP、注册和 fixture 放入 `tests/support/`，每个测试文件保持一个资源域。

### 目录层级不足，文件名前缀代替模块边界

**定性：违反用户确认的结构约束，严重，必须与超长文件重构一并处理。**

当前目录未能表达完整的业务层级，多个目录在同一层堆放平级文件，再以文件名前缀区分下级概念：

- `src/entity/` 的 9 个实体文件中，8 个以 `identity_` 开头，例如 `identity_endpoint_configs.rs`、`identity_provider_models.rs`、`identity_request_logs.rs`。
- `src/bridge/stream/` 同时以 `decode_`、`encode_` 和协议名组合区分职责，例如 `decode_anthropic.rs`、`decode_responses.rs`、`encode_anthropic.rs`、`encode_responses.rs`。
- `src/bridge/` 在同一层并列 `anthropic_decode.rs`、`anthropic_encode.rs`、`responses_decode.rs`、`responses_encode.rs`，协议和方向只能从文件名拼接理解。
- `tests/` 将扩展、身份、schema 等领域放在同一层，以 `extensions_`、`identity_`、`schema_` 前缀区分；其中 `management_isolation.rs` 还把多个管理资源重新混装进一个文件。

这不是命名风格问题。目录未承载领域和协议边界时，新增一个实体、桥接方向或测试资源只能继续复制前缀并堆入原目录；文件过长、`mod.rs` 过度聚合和测试交叉正是这一结构的后果。

重构应让路径直接表达归属，而不是将前缀原样搬进更多文件：

- 将 `entity/identity_*.rs` 收敛到 `entity/identity/`，按 Provider、接入点、模型、请求记录和会话继续分组；`entity/mod.rs` 只汇总实体模块。
- 将桥接按协议和流向分组，例如 `bridge/anthropic/{decode,encode}.rs`、`bridge/responses/{decode,encode}.rs`，以及 `bridge/stream/{decode,encode}/`；事件、SSE 与 pipeline 保持在流公共层。
- 将 `schema.rs` 改为 `schema/` 模块，分离表定义、索引和初始化编排；避免根目录继续累积持久化细节。
- 将 `tests/` 按 `extensions/`、`identity/`、`schema/`、`management/`、`v1/` 划分，公共 fixture 仍放在现有 `tests/support/`；各目录只覆盖一个稳定资源域。
- 公开协议路由拆分时，使用 `routes/v1/<protocol>/` 承载该协议的入口、候选执行、观测和测试，不在 `routes/v1/` 继续增加以协议名命名的大文件。

### 同一实现文件承载生产代码与大规模内联测试

**定性：违反用户确认的硬性结构约束，严重，必须重构。**

`images.rs`、`chat.rs`、`providers/spec.rs`、`storage/stats.rs`、`schema.rs` 和多个 bridge 文件在 `#[cfg(test)] mod tests` 后继续累计数百行测试。虽然部分文件的生产区低于 450 行，物理文件仍超过阈值，且生产改动与测试夹具在同一差异中耦合。

建议对每个此类模块采用 `module.rs` 加 `module_tests.rs` 或同级 `tests/` 子模块形式。测试保留访问私有实现所需的最小 `pub(crate)` 边界，不要为迁移测试扩大公开 API。

## 整改优先级建议

### 先拆公开协议路由

- 先处理 `responses.rs`、`messages.rs`、`images.rs` 与 `chat.rs`，因为它们直接承载外部协议、候选切换和敏感观测逻辑。
- 同步建立 `routes/v1/<protocol>/`、`bridge/<protocol>/` 和 `bridge/stream/{decode,encode}/`；先迁移模块边界，再在边界内拆分实现，避免用更多前缀文件替代结构。
- 每完成一个路由域，运行其聚焦路由与身份隔离测试，再运行全量 Rust 门禁；任何新文件均不得超过 450 行。

### 再拆持久化与 schema

- 以现有 `Storage` 子模块为落点移动实现，不新建平行存储抽象。
- 将 `entity/identity_*.rs`、表结构与索引按实体迁入对应目录，保持一次性初始化和 SQLite/PostgreSQL 的既有语义。

### 最后拆桥接与集成测试

- 按协议方向拆 request decoder、content/tool decoder 和测试，不改变协议 DTO。
- 将集成测试 fixture 集中到已有 `tests/support/`，保持每个测试文件单一资源边界。
