## 主要问题

### Cargo 构建脚本自动修复问题已处理

问题定性：历史问题已整改，后续保持检查和修复分离。

证据：

- 提交 `82383dc 收口构建检查治理` 已调整构建检查入口。
- 当前 `build.rs` 执行 `bun run format:check`、`bun run lint` 和 `bun run build`。
- 当前 `build.rs` 不再执行 `bun run format` 或 `bun run lint:fix`。
- `web/package.json` 已提供 `format:check`。

剩余风险：

- Rust 检查路径仍会触发前端检查和构建，耗时和职责边界需要在后续开发文档或 CI 设计中继续明确。
- 如果后续新增前端脚本，仍需避免把自动修复动作接回 Cargo build script。

建议：

- 保持 `build.rs` 只执行 check-only 和 build 命令。
- 把前端检查命令和 Rust 检查命令的职责边界写入开发文档或 CI 配置。
- 后续如果要调整 Cargo build script，不要引入会修改源码的命令。

### 流式桥接模块职责过重

问题定性：已优化，后续关注真实事件差异。

证据：

- `src/bridge/stream.rs` 文件约 37 KB。
- 该文件同时包含 SSE 行解析、Chat SSE decoder、Responses SSE 到 Anthropic SSE 转换、Anthropic SSE 到 Responses SSE 转换、Responses SSE 编码、Anthropic SSE 编码和测试。

已完成：

- `stream.rs` 已拆为 `stream/` 模块目录。
- Responses / Anthropic Messages 流式 tool call、usage、finish reason 已进入内部事件层。
- 流式 recorder 已能从内部事件统计 usage、tool call 数和完成状态。

剩余风险：

- 未识别流式事件当前不会中断流，但还没有正式写入 diagnostics metadata。
- 真实客户端可能发送 mock 未覆盖的事件形态。

### 路由文件承担过多适配和日志职责

问题定性：建议优化。

证据：

- `src/routes/responses.rs` 文件约 60 KB。
- `src/routes/messages.rs` 文件约 55 KB。
- 两个文件内重复出现上游请求、错误处理、流式分支、request log 构造和 mock upstream 测试。

风险：

- 每新增一个统计字段或 metadata 字段，都需要在多个分支手动同步，容易遗漏。
- 错误观测、上游 request id、流式日志写入策略在不同路径表现不一致。
- 路由层承担协议转换细节，不利于后续真实客户端问题定位。

建议：

- 先抽 `RequestMetadataBuilder` 和日志构造辅助，减少 route 手写 JSON 和重复字段。
- 在 stream pipeline 稳定后，再抽上游调用和流式响应构造。
- 保持路由层职责为鉴权、模型解析、协议选择和响应返回。

### 兼容动作结构化诊断已接入非流式主链路

问题定性：主干已整改，剩余边界在流式和详情展示。

证据：

- `decode_responses_request`、`decode_anthropic_request` 已对未知 role、未知 tool、非文本内容做兼容处理。
- 后端提交 `f06bf64 记录桥接兼容诊断` 后，已新增 `BridgeDiagnostic` 和 request metadata schema。
- Chat、Responses、Messages 请求日志已写入 bridge metadata / diagnostics。
- 前端提交 `7b907b0 展示请求诊断 metadata` 后，请求日志列表已展示 diagnostics 摘要和 warning 标记。

剩余风险：

- 未识别流式事件还没有纳入 diagnostics metadata。
- 真实 Codex / Claude Code 可能发送 mock 没覆盖的新字段，仍需要通过联调补 diagnostics code。

建议：

- 保持 request log metadata 使用稳定 schema，不记录完整用户输入。
- 在 stream pipeline 中接入 stream diagnostics。
- 增加 typed metadata 详情展示，避免只靠摘要判断问题。

### Stats API metadata 基础暴露已处理

问题定性：历史问题已整改，typed metadata 详情展示已补齐。

证据：

- `request_logs` 表存在 `metadata_json` 字段。
- `src/stats.rs` 的 `RequestLogSummary` 已包含 `metadata_json`。
- `list_requests` 已查询并返回 `metadata_json`。
- `web/src/api/index.ts` 的 `RequestLogSummary` 已包含 `metadata_json: string | null`。
- `web/src/views/StatsView.vue` 已在最近请求表格展示 diagnostics 数量和 warning 标记。

剩余风险：

- 旧日志和异常 JSON 已有降级显示，但详情页还没有统一的信息边界。
- 原生 Responses / Anthropic Messages 直通流 usage 仍未归一化进统计字段。

建议：

- 保持旧日志兼容，metadata 为空或解析失败时正常显示。
- 后续增加 typed metadata 详情展示。
- 流式 recorder 完成后，把 stream 汇总纳入同一 metadata 视图。

### 流式统计缺少结束态回填

问题定性：已优化，仍有原生透传边界。

证据：

- `src/routes/stream_stats.rs` 的 `record_first_chunk` 在首个 bytes chunk 到达时插入日志。
- 当前没有 `UPDATE request_logs` 类结束态回填路径。
- 实现状态文档也记录流式 token、tool-call 数和上游 request id 多数没有准确回填。

已完成：

- 固定 log id + 结束 update 已补齐。
- completed、empty、final_usage_seen、stream_error 已进入 metadata。
- 桥接流式路径的 usage 和 tool_call_count 能在结束时回填。

剩余风险：

- 原生直通 Responses / Anthropic Messages 流暂不解析 usage。
- 上游 request id 仍依赖具体协议和 provider 可提取性。

### 仓库文本治理配置已补齐

问题定性：基础配置已存在，后续避免混入行尾治理噪音。

证据：

- 提交 `82383dc 收口构建检查治理` 已补齐文本治理配置。
- 仓库自身已有 `.editorconfig`。
- 仓库自身已有 `.gitattributes`。
- 当前同时包含 Rust、Vue、TypeScript、Markdown、Shell、Dockerfile。

剩余风险：

- `.editorconfig` 中 Markdown 允许保留尾部空白，文档改动仍要用限定范围检查避免误判全仓旧问题。

建议：

- 保持文本治理作为独立工程治理任务处理。
- 不在协议行为重构提交里顺手规范化行尾。
- 文档提交使用限定路径的 `git diff --check`。

问题定性：规范缺失导致风险。

证据：

- 当前工作树存在 `.refs/` 参考项目目录。
