# Prelay 当前工作树与活动存储工程评审报告

## 评审范围

本次只评审 `prelay-server`、`prelay-client`、`prelay-protocol` 当前工作树中的工程状态、活动 rollout 存储实现、跨仓契约和验证门禁，不评价功能需求完成度，也不把业务交互偏好当作工程问题。

评审主范围：

- `prelay-server` 当前未提交工作树，包括活动 rollout 文件存储、Anthropic 协议移除、图片预算、供应商协议能力和 schema 迁移。
- `prelay-protocol` 当前未提交工作树，包括协议枚举、供应商协议地址和 Bruno 示例。
- `prelay-client` 当前未提交工作树，以及分支上已有的两个未推送扩展包提交的发布门禁状态。

已确认的边界：

- 活动正文不设应用层大小上限，属于已确认的产品边界，不列为问题。
- 活动文件不做自动清理，属于已确认的运维边界，不列为问题。
- 当前按单机本地盘部署，不把多实例共享文件系统列为问题。
- 多站点控制面设计尚未结束，不纳入本次评审。

审查方式为评审时只读审查和构建/测试检查；评审当时只新增本报告，没有修改业务代码。后续整改结果见“整改后状态”。

## 评审依据

- 工作区 `AGENTS.md`：三个子仓独立提交；协议 DTO 和稳定错误码先修改 `prelay-protocol`，再更新父仓 submodule 指针；不能在三个仓库并行复制类型定义。

## 总体结论

当前工作树不能直接提交或进入发布流程。已有三个发布级阻断：协议子仓改动没有落到父仓 gitlink；服务端结构门禁失败；客户端格式门禁失败。

活动 rollout 文件存储的方向本身可行，但“文件是唯一正文源”的承诺与实际数据库会话存储不一致，文件、索引和活动状态没有统一所有权。流式结束状态、会话标识和事件完整性也存在语义缺口。即使解决发布门禁，这些问题仍会影响活动审计、会话续接和后续记忆消费。

### “文件是唯一正文源”与 `identity_response_sessions` 冲突

问题定性：违反项目已确认设计契约，高风险；同时存在数据安全和一致性问题。

证据：

- `docs/superpowers/specs/2026-10-22-activity-rollout-storage-design.md:7,21` 声明文件是唯一正文源，不把完整正文复制进 PostgreSQL。
- `src/storage/sessions.rs:52-53` 仍把完整 `input_messages` 和 `response.output` 序列化到 `identity_response_sessions`。
- `src/bridge/internal.rs:151-158` 的 `InternalImagePart` 保存完整 `image_url`，data URL/base64 图片也会进入该数据库字段。
- JSONL 写入前会执行 redaction，`identity_response_sessions` 这条路径没有对应脱敏。

风险：

- 同一对话正文至少存在两份，文件、数据库和后续 memory worker 可能读到不同版本。
- 数据库中的 response session 可能包含未脱敏的 prompt、工具返回或内联图片数据，绕过了活动文件的脱敏边界。
- 记录“文件唯一源”后，后续清理、迁移、备份和记忆消费无法确定哪一份是权威数据。

建议：

- 二选一：将 response session 缩小为协议续接所需的最小状态和引用；或明确承认第二个正文源，并为其定义脱敏、保留、备份和一致性规则。
- 如果保留 response session 正文，必须让它和 activity rollout 使用同一套 redaction 和 access 边界。

### 文件、活动索引和活动状态没有统一所有权

问题定性：违反项目已确认规范，高风险。

证据：

- `AppState` 同时暴露 `Storage` 和 `RolloutStore`，见 `src/lib.rs:35`。
- `src/storage/rollouts.rs:72-85` 启动时只更新 `activity_rollouts.status`，不更新 `identity_activities.status`。
- 流式活动开始时会把 `identity_activities.status` 写成 `streaming`，见 `src/observability/stream_stats/state.rs:158`。
- 项目数据库文档要求 `Storage` 是唯一持久化入口，见 `docs/architecture/database.md:29`。

风险：

- 进程在流开始后崩溃，`activity_rollouts` 会变成 `partial`，但活动主表可能永久保持 `streaming`，活动列表和统计会显示未结束。
- 文件写成功、数据库写失败时没有业务层统一状态机处理；路由、观测和清理代码分别理解“完成”和“失败”。
- 后续增加读取或记忆 worker 时，无法确定应以 activity、rollout 还是文件状态为准。

建议：

- 增加一个统一的 `ActivityStore`/`ActivityRecorder`，由它拥有文件、`activity_rollouts` 和 `identity_activities` 的状态转换。
- 明确 `identity_activities.status` 与 `activity_rollouts.status` 的映射和启动恢复事务。
- 将启动恢复测试覆盖到活动主表和活动文件两侧，而不只检查 `activity_rollouts`。

### 流式 EOF 会把未完成流标记为成功

问题定性：违反项目已确认生命周期要求，高风险。

证据：

- `src/observability/stream_stats/state.rs:224-248` 的 `record_stream_end` 在普通 EOF 时直接写 `status: "success"`，随后调用 `finalize_rollout(RolloutStatus::Completed, Some(200), ...)`。
- 原生 Responses SSE 只有收到 `response.completed` 才设置完成标志；图片流也只有收到 `image_generation.completed` 才设置完成标志。
- `src/observability/stream_stats/state.rs:424-429` 在终结时并不检查 `snapshot.completed` 或图片 capture 的完成标志。

风险：

- 上游或网络代理在发送部分 SSE 后干净关闭时，客户端收到截断流，活动却记为成功、rollout 记为 completed。
- 没有完成事件时不会保存 response session，后续使用该 response ID 续接会失败。
- 该问题会直接削弱“活动文件可作为审计或记忆来源”的可信度。

建议：

- 终结时检查协议完成标志；缺失完成事件应标记 `partial` 或 `failed`，并写入明确错误。
- 为没有完成事件的原生 Responses、Chat bridge 和图片流增加测试。

### `session_id` 实际是上一轮 response ID，不是稳定会话键

问题定性：设计规范不完整，中风险。

证据：

- 设计文档把 `session_id` 定义为会话关联和数据库聚合字段，见 `docs/superpowers/specs/2026-10-22-activity-rollout-storage-design.md:43`。
- Responses 路径直接把 `previous_response_id` 作为 `session_id` 传入：
  - `src/routes/v1/responses/native.rs:366`
  - `src/routes/v1/responses/chat.rs:347`
- `src/activity/mod.rs:40-44` 随后将该值写入 session meta 和 rollout 索引。

风险：

- 第一轮使用 activity_id，第二轮使用上一轮 response ID，第三轮使用第二轮 response ID；同一会话的每轮活动落在不同 session。
- 按 session 聚合、记忆幂等和清理无法得到稳定的会话边界。

建议：

- 明确 `activity_id`、`conversation_id`、`previous_activity_id` 三个概念。
- 如果当前设计只记录上一轮引用，应将字段改名为 `previous_response_id` 并取消“会话聚合”承诺。
- 如果需要会话聚合，在 response session 中增加稳定的 conversation ID，并沿续接链传递。

### “完整事件序列”与实际的流式汇总格式不一致

问题定性：违反项目已确认设计契约，中风险。

证据：

- 设计目标是保存完整事件序列，包括推理、用量和结束状态，见 `docs/superpowers/specs/2026-10-22-activity-rollout-storage-design.md:11-13`。
- `src/observability/stream_stats/record.rs:176-179` 对流式记录传入 `content_capture: None`。
- `src/activity/events.rs:153-184` 只生成最终文本、最终工具调用和用量，没有逐块事件、推理事件或媒体引用。
- `SessionMetaEvent` 没有 schema version，见 `src/activity/rollout.rs:94-106`。

风险：

- 名为完整事件序列，实际是最终响应摘要；无法回放流式过程、推理或媒体内容。
- JSONL 格式未来变化后，旧文件和后续 memory worker 没有版本判断依据。
- 设计说图片、音频和附件“单独存文件”，但当前没有媒体文件存储和路径写入，只有类型、大小和 hash 元数据。

建议：

- 明确 JSONL 是“最终对话内容”还是“可回放事件流”。
- 若选择最终内容，修正设计文档和事件命名，不再声称完整事件序列。
- 若选择事件流，增加 schema version、逐事件写入、推理事件和媒体文件引用。

### 无大小上限的接受边界与当前内存缓冲实现不匹配

问题定性：违反硬性工程基线，中风险。这里不挑战“无存储上限”的产品边界，只指出无上限正文不能长期驻留内存。

证据：

- `src/bridge/stream/events.rs:147-148` 持续把输出追加到 `String`。
- `src/activity/stream.rs:171` 也持续累积输出文本。
- `src/activity/events.rs:159` 在终结时再次克隆完整输出。
- `StreamStatsSnapshot` 没有对应的内存上限或流式落盘策略。

风险：

- 超长流式响应会让进程持有完整输出及其克隆副本，可能造成内存压力。
- 文件写入虽然有上限压力测试，但测试只证明能写大内容，没有证明进程在处理超长流时保持有界内存。

建议：

- 保留无存储上限，但将输出流式追加到文件或临时缓冲，不在内存中保存完整字符串。
- 为超长流做内存峰值和写入背压验证，不要通过新增正文大小上限规避。

### 脱敏边界没有覆盖 Cookie 和 Basic Authorization

问题定性：违反项目已确认安全边界，高风险。

证据：

- 设计明确要求不保存 Authorization、Cookie、API Key、Endpoint Token 或设备凭据，见 `docs/superpowers/specs/2026-10-22-activity-rollout-storage-design.md:70`。
- `src/activity/redaction.rs:9-23` 的赋值模式没有 `cookie` 或 `set-cookie`。
- `Authorization: Basic <base64>` 只会替换掉 `Basic`，后面的凭据值不在该正则的值范围内。
- 现有测试只覆盖 Bearer。

风险：

- 用户消息或工具输出中的 Cookie 和 Basic 凭据可能原样写入 JSONL。
- 脱敏结果不能支撑“所有活动正文都经过凭据脱敏”的承诺。

建议：

- 增加 Cookie、Set-Cookie、Basic Authorization、Proxy-Authorization 等模式测试。
- 对结构化 header-like 内容优先按字段替换，不仅依赖自由文本正则。

### 图片 prompt 的持久化行为与现有协议文档相反

问题定性：文档漂移，中风险。

证据：

- `src/activity/events.rs:112-124` 将图片生成 `prompt` 写入 rollout JSONL。
- `docs/architecture/images-generation.md:37,43` 明确写“服务端不保存提示词”“提示词不进入记录”。
- `src/routes/v1/images/tests/activities.rs:4` 的测试名写 `without_image_or_prompt_content`，但只在 `:56-65` 检查活动摘要，没有检查 rollout 文件。
- `tests/v1/identity_scope.rs:290` 则明确断言 rollout 中存在 prompt。

风险：

- 数据保留边界、用户可见的隐私承诺和实际存储行为互相矛盾。
- 现有测试名称会给出错误的脱敏覆盖印象。

建议：

- 如果保存 prompt 是预期行为，更新图片协议文档和测试名称，并增加 rollout 级 prompt 断言。
- 如果不保存 prompt，删除 `events_from_image_request` 的正文写入，并增加 rollout 负断言。

### 上游超时覆盖不完整，文档表述大于实现

问题定性：文档漂移，中风险。

证据：

- `src/upstream.rs:97-116` 新增的 `send_with_timeout` 只被 Responses 路径调用：
  - `src/routes/v1/responses/native.rs:93`
  - `src/routes/v1/responses/chat.rs:77`
- `/v1/chat/completions` 和 `/v1/images/generations` 仍直接调用 `.send()`：
  - `src/routes/v1/chat/candidate.rs:50`
  - `src/routes/v1/images/candidate.rs:47`
- `README.md:100` 和 `deploy/.env.example:23` 将“上传 + 等待响应头”的约束描述成全局行为。

风险：

- 大请求在 Chat 或图片入口遇到不读取请求体、也不返回响应头的上游时，仍可能拖到下游网关超时。
- 运维人员按文档认为超时已全局生效，实际只覆盖 Responses。

建议：

- 将 `send_with_timeout` 接到所有上游请求入口，或收紧 README 和 `.env.example` 的适用范围。
- 增加 Chat、图片入口的响应头超时测试。

### Docker 本地盘目录的可写性没有启动检查

问题定性：规范缺失导致的部署风险，中风险。

证据：

- `Dockerfile:20` 使用 `USER relay`，容器用户 UID 为 1000。
- `deploy/docker-compose.yml:13` 直接挂载主机 `./data/sessions` 到 `/app/data/sessions`。
- `src/main.rs:161-185` 启动扫描只读取 `.part` 文件，不验证目录可写。

风险：

- Linux 上如果 `deploy/data/sessions` 由 Docker 自动创建为 root 所有，服务仍能启动，但首个聊天/Responses 流请求会因写入失败返回 500。
- 单机本地盘是已确认边界，但目录权限没有形成启动时可见的部署错误。

建议：

- 启动时验证 `ACTIVITY_ROLLOUT_DIR` 存在、可写且不是普通文件。
- 在部署文档中说明目录预先创建和 UID/GID 1000 权限，或在镜像/Compose 中显式处理。

### 启动迁移会直接删除旧数据，缺少预检和回滚说明

问题定性：规范缺失导致的风险，中风险。

证据：

- `src/schema/activity_rollout.rs:26` 在 schema 初始化中直接执行 `DROP TABLE IF EXISTS activity_contents`。
- `src/schema/anthropic_removal.rs:92` 删除协议为 Anthropic 的活动记录。
- `src/schema/anthropic_removal.rs:58-59` 还会清理供应商记录和 Anthropic 能力字段。
- 设计明确旧正文不做迁移，直接删除。

风险：

- 首次启动新版本会在无交互确认的情况下删除旧正文和相关活动，操作不可逆。
- 数据库记录被删除，但对应的 rollout 文件和 response session 可能仍然存在，形成数据边界不一致。
- 当前没有迁移前备份、dry-run 或回滚说明。

建议：

- 在发布说明中明确迁移会删除的数据范围，并要求数据库和 `ACTIVITY_ROLLOUT_DIR` 的备份。
- 增加迁移前统计和 dry-run 或独立的维护模式，至少让部署方看到将被删除的行数和文件数。
- 明确 Anthropic 活动文件、response session 和数据库中活动记录的同步删除策略。

### `read_events` 未实现计划中的部分行处理，孤儿文件扫描也不完整

问题定性：建议优化，低风险。

证据：

- 实现计划要求 `read_events` 对未完成最后一行返回带有效前缀的 `PartialLine`，见 `docs/superpowers/plans/2026-10-22-activity-rollout-storage.md:273`。
- 实际 `src/activity/rollout.rs:264-270` 直接按行反序列化，末尾不完整行只会返回普通序列化错误。
- `src/main.rs:161-185` 只扫描 `.part` 文件；没有索引的完整 `.jsonl` 孤儿文件不会产生告警。
- 设计描述启动扫描无索引孤儿文件，但当前没有实现完整 `.jsonl` 的扫描和索引重建。

风险：

- 数据库写失败留下的完整 JSONL 可能长期不被发现。
- 后续 memory worker 读取部分文件时，无法区分“文件损坏”和“最后一行未写完”。

建议：

- 实现 `PartialLine { path, valid_events }` 或等价错误类型。
- 启动时同时扫描 `.part` 和无索引 `.jsonl`，至少输出可操作的告警或重建建议。

### 完整性元数据目前基本只写不读

问题定性：建议优化，低风险。

证据：

- `activity_rollouts` 的 `event_count`、`byte_size`、`sha256`、`last_error` 只在写入路径出现。
- 当前没有读取路径校验 hash、比较 byte size 或依据 `last_error` 恢复。
- `session_id` 索引也没有对应的查询入口。

风险：

- 设计中的审计和恢复价值没有形成闭环，元数据只增加 schema 复杂度。
- 文件被截断或替换时，数据库没有校验入口发现。

建议：

- 如果后续 memory worker 需要，增加读取时 hash/size 校验和失败状态。
- 如果暂不实现，按项目简约原则删除未使用字段或明确其后续消费者。

### 文档和规则仍有局部漂移

问题定性：建议优化，低风险。

证据：

- `docs/architecture/database.md:29` 仍写 `AppState` 只持有 `Storage`，实际还持有 `RolloutStore`。
- `prelay-server/AGENTS.md:11` 仍写请求统计不默认保存完整 prompt 或响应正文；活动文件现在会保存完整正文，需要区分“统计”和“活动正文”的职责。
- 工作区根目录存在一个 105 字节的 `$null` 文件，不属于三个 Git 仓库。

建议：

- 更新 `AppState` 和活动正文/统计职责文档。
- 确认 `$null` 是否为误生成产物，再决定删除；不要未经确认把它纳入任何仓库。

## 整改优先级建议

### 第一优先级：发布阻断

- 提交并验证 `prelay-protocol`，更新 server/client 的 submodule 指针。
- 拆分 `image_budget.rs`、`stream_stats/state.rs`、`stream_stats/tests.rs` 和 `providers/responses.rs`，恢复 450 行结构门禁。
- 修复客户端 11 个 Prettier 失败文件，重新执行 `format:check`。

### 第二优先级：活动存储一致性和安全

- 明确 `identity_response_sessions` 是正文副本还是最小协议状态，消除“唯一正文源”矛盾。
- 统一 `identity_activities.status`、`activity_rollouts.status` 和文件终结状态的所有权与恢复逻辑。
- 修正 `session_id` 语义，定义稳定的 conversation ID 或改名为 previous response ID。
- 补齐 Cookie、Basic Authorization 等脱敏路径，并统一 JSONL 与 response session 的脱敏边界。
- 对没有完成事件的流式 EOF 写入 failed/partial，不标记 success。

### 第三优先级：事件格式和运维验证

- 明确 JSONL 是最终内容还是完整事件流，并增加 schema version、推理事件和媒体引用。
- 将无上限输出改为流式落盘，避免完整正文长期驻留内存。
- 为 JSONL 和 response session 增加一致性检查、hash/size 校验或恢复任务。
- 说明启动迁移的数据删除范围、备份要求和不可逆性。
- 在隔离 PostgreSQL 数据库执行 schema、迁移、清理和路由测试；在当前环境补齐 `TEST_POSTGRES_URL` 后再判断全链路可用性。
