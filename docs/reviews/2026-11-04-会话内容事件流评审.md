# Prelay Server 会话内容事件流评审报告

## 评审范围

本次评审对象是 `v0.4.4..HEAD`（4 个提交，HEAD `237fec8`）引入的会话内容事件流改造，包括：

- v1 线程文件格式与写入端；
- legacy 读取兼容与索引版本升级；
- 活动、流式、Responses、Chat、图片链路的接入；
- 会话展示、记忆、审计读取边界；
- 0.4.5 版本收口与发布就绪性。

本次只评审工程体系、数据边界、兼容策略、质量门禁和发布风险，不评价功能需求完成度、业务规则正确性，也不把真实上游联调结果纳入结论。

- 本次实际执行的命令输出与 Git 状态。

## 总体结论

改造方向与规格一致：线程文件确实成为唯一内容事件源，历史回放只写引用，索引不保存正文，旧文件和旧索引有可执行的兼容路径，质量门禁全部通过。

评审时有三项影响发布质量的问题应先处理：README 仍描述旧事件格式和旧去重语义；原生 Responses 的 `context` 在图片预算改写后不再等于模型实际输入；工具参数脱敏范围过宽，会永久丢失部分工具输入。第四项为原生直通链路的端到端测试缺口，建议随后补齐。

评审后已完成上述问题整改，处理结果和复验证据见“整改结果”一节。

## 主要问题

### README 活动正文说明与新实现不一致

**定性：违反项目已确认规范（文档与代码漂移）。**

`README.md:119` 仍写着：

- 按 `(type, payload)` 事件身份和出现次数去重；
- `previous_response_id` 的直通请求“只携带当前增量，必须直接追加，不能按历史回放去重”；
- 窗口变化写 `window_start`；
- 索引 version 1 失效重建。

当前实现已经改变：

- `append_request_events` 先按稳定 `item_id` / `tool_call_id` 匹配，再按内容身份和当前窗口出现次数兜底（`src/store/rollout/writer.rs:265`）；
- `previous_response_id` 路径会先拼入父轮请求/响应项，再按回放去重（`src/inbound/v1/responses/candidate.rs:68`）；
- 窗口事件类型为 `window`（`src/store/rollout/writer.rs:157`）；
- 索引版本为 3（`src/store/rollout/index.rs:19`），版本 1 和 2 都会失效重建。

风险：运维和后续维护者按 README 理解回放行为，会误判重复正文、跨版本升级和索引兼容；发布说明也容易沿用错误描述。

建议：重写该段，明确 v1 文件头、`window`/`turn`/`context`/`turn_end`、稳定 ID 优先的去重顺序、legacy 混合文件行为和索引版本 3。

### 图片预算改写后，context 不再等于模型实际输入

**定性：违反项目已确认规范。**

`candidate.rs:68` 在预算处理之前，用未裁剪的 `input_items` 生成请求内容事件；`native.rs:62` 随后才执行 `budget_input_items`，把超预算的历史图片替换成 `input_text` 占位文本（`src/inbound/v1/responses/image_budget.rs:214`）。

结果是：文件中的请求内容仍是 `input_image` 占位，而模型实际收到的是“历史图片已被服务端图片预算省略”的文本。规格要求 `context` 保存“模型本轮实际看到的完整输入顺序”，当前记录与实际上游输入不一致。

风险：审计无法据 `context.refs` 还原真实输入；后续记忆提炼会把未发送的图片占位当成已发送内容。该差异会随图片预算启用而持续写入文件。

建议：在预算处理完成后生成请求内容事件，或把预算结果回传给候选层再生成事件；补一条启用图片预算的原生 Responses 集成测试，断言文件内容与上游请求体一致。

### 工具参数脱敏范围过宽

**定性：违反项目已确认规范（工具输入完整性）。**

`sanitize_json` 会对工具参数和工具结果递归删除 `filename`、`file_name`、`file_id`、`hash`、`sha256`、`size_bytes` 等键（`src/codec/activity/conversation.rs:23`、`:255`、`:288`），并不区分该字段属于附件还是普通工具输入。

同时，`looks_like_binary` 把长度不小于 256 且只含 base64 字母表字符的字符串整体替换为 `{"type":"binary","omitted":true}`（`src/codec/activity/conversation.rs:301`）。长标识符、长哈希或压缩文本可能被误判。

规格只要求图片、文件、音频不保存正文、base64、hash 和文件名，并保留 `type + omitted` 占位；没有要求删除普通工具参数中的文件名字段。

风险：`read_file`、`exec_command` 等工具的真实输入会被永久裁剪，审计和记忆无法还原工具调用意图；已写入文件的内容无法通过后续修复补回。

建议：把附件判定收敛到 media content part 或明确的附件对象；文件名和哈希只在附件结构内部丢弃；二进制识别限定在 `data:`、`b64_json`、`file_data` 等明确载体，避免按长度启发式判断。

### 原生 Responses 直通链路缺少端到端内容断言

**定性：规范缺失导致风险（测试覆盖缺口）。**

活动相关集成测试使用 Chat Completions 上游（`src/inbound/v1/responses/tests/activities.rs:5`）；原生 Responses 夹具只返回文本消息和 usage（`src/inbound/v1/responses/tests/fixtures.rs:144`），使用它的测试只断言路由和响应状态。

本轮把响应内容来源从 `InternalMessage` 改为原始 Responses `output`，新增了 reasoning 双字段、`custom_tool_call`、refusal 和 usage 的归一化。单元测试覆盖了归一化函数，但没有覆盖“原生上游 → 响应写盘 → 文件内容”的接线。

风险：如果候选层把错误的 `request_events` 或响应输出传给 writer，现有测试不会失败；这类错误只在真实调用后才暴露。

建议：给原生 mock 增加 reasoning（summary 与 content 同时存在）、`custom_tool_call`、refusal 和 usage，断言线程文件中的事件类型、`message_phase`、`context.refs` 与 usage 字段。

### 事件计数与事件列表语义不一致

**定性：建议优化（接口语义）。**

`RolloutFile.event_count` 取自 `parsed.line_count`（`src/store/rollout/read.rs:61`），包含 v1 文件头；`events` 不包含文件头（`src/store/rollout/read.rs:297`）。`RolloutSlice.event_count` 同样统计选中行数（`src/store/rollout/read.rs:115`）。数据库 `activity_rollouts.event_count` 也包含首个活动写入的文件头行。

风险：调用方用 `event_count` 校验事件数量时会差 1；legacy 文件没有文件头，两者又恰好相等，容易形成错误预期。

建议：拆分 `line_count` 与 `event_count`，或统一事件计数的定义并补测试；数据库字段含义在 README 中说明。

### 续写 legacy 文件后格式标记只描述文件头

**定性：建议优化（兼容语义）。**

新文件首次创建时写入 v1 文件头，`format` 置为 `V1`；已有 legacy 文件续写时保留 `state.format`（`src/store/rollout/writer.rs:102`），即使尾部追加的是 v1 事件。读取端以首行判定格式（`src/store/rollout/read.rs`）。

风险：读取方看到 `Legacy` 可能误以为文件内不存在 v1 事件，也可能据此跳过 `context` 解析。

建议：将字段语义命名为文件头格式，或在文档和读取接口注释中明确“混合文件”的行为；如需严格区分，按行解析事件版本。

### 索引体积与写入放大缺少本轮基准

**定性：建议优化（容量与性能验证缺口）。**

索引现在为每个内容身份保存完整 `seq` 列表，并为稳定 ID 保存引用（`src/store/rollout/index.rs:44`），同时 `item_refs` 随事件增长。每次 `finish` 重写整份索引。长线程 benchmark 仍为 ignored，本轮没有复测。

风险：超长线程的索引文件会随事件数线性增长，写入耗时和磁盘占用上升；当前结论只有功能测试支撑，没有容量证据。

建议：用现有 benchmark 或真实长线程测量索引大小与 `finish` 耗时，确认在保留策略下可接受；必要时改为分页或只保留窗口内引用。

整改后已复测，数据见“整改结果”。

### 首个实现提交的描述超前于实际内容

**定性：建议优化（提交可追溯性）。**

`644e5ac` 的正文写“新增 v1 会话内容事件和正文草稿类型”，但 `ConversationFormat`、`ConversationEvent`、`WindowEvent` 等 v1 文件类型在 `dd6e64d` 才加入。按提交逐个阅读时，第一个提交找不到 v1 文件头实现。

风险：历史追溯需要跨提交拼合，影响审查效率。

建议：后续拆分提交时让正文只描述该提交实际交付物；该提交尚未推送，如需整理可在发布前 amend，但不是发布阻塞项。
