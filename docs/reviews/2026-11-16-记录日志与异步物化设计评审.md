# Prelay 记录日志与异步物化设计评审报告

## 评审范围

本次评审对象是 `docs/superpowers/specs/2026-11-15-recording-journal-async-materialization-design.md` 的当前版本。重点判断设计与当前 `prelay-server` 的 Rust、Axum、Tokio、SeaORM、PostgreSQL、线程 JSONL 和 Docker 部署是否匹配，以及是否真正解决请求路径上的同步记录问题。

本次不评价 `/v1` 业务协议、接入点业务规则或客户端功能，也不把设计文档当成已经实现的能力。评审时未修改生产代码；评审后按基线阶段增加了计时日志，尚未实现 WAL。

## 评审依据

- `review-engineering` 通用工程基线及 Rust 专项清单。
- `prelay-server/AGENTS.md` 中的数据边界、验证要求和部署约束。
- 当前服务端代码、Dockerfile、`deploy/docker-compose.yml`、README 和已有活动内容设计。
- 设计文档中的时间语义、WAL、提交边界、物化、恢复、故障语义、可观测性、迁移和验收章节。

## 总体结论

设计方向正确，与当前服务端职责边界一致：服务端继续做 `/v1` 代理，接入点解析、故障迁移和 Provider Key 管理不被搬到客户端；WAL 只承接记录持久化，数据库和线程 JSONL 仍是查询与展示来源。

当前版本已经覆盖关键设计缺口：

- WAL 记录携带原始 `started_at`、`first_token_at`、`finished_at` 和内容事件时间，物化器不再用当前时间代替请求时间。
- `RecoveryCoordinator` 统一 WAL 回放、既有 `recover_interrupted`、孤儿告警和身份清理顺序。
- 明确 `data/recording` 持久卷、环境变量、权限和备份要求。
- 增加每线程写入 actor，区分异步锁获取和阻塞文件写入。
- 增加 materialization lag SLO、degraded/blocked 健康状态和 pending 可见性边界。
- 增加 `fsync` 超时、pending identity 清理门禁、随机 epoch 和克隆目录策略。
- 把 WAL 写放大列为非目标和基线 go/no-go，而不是隐含收益。

结论是：**设计方向有条件通过，可以进入实现计划；但不能跳过基线测量直接全量实现。**

仍然成立的条件是高优先级：

- WAL 保存完整内容并再次写入线程 JSONL，写放大和首尾延迟必须用真实 payload/并发验证；如果磁盘吞吐成为新瓶颈，本设计不适用。
- 当前部署清单还没有 `data/recording` 卷和 `RECORDING_JOURNAL_DIR`，必须在实现批次同步修改，不能留到部署时补。
- 5 秒 materialization lag SLO 是设计默认值，产品是否接受“成功响应后统计/会话短暂滞后”仍需确认。

## 设计优点

- 职责划分清楚：请求处理器、Journal、GroupCommitter、Materializer、Recovery 和现有存储适配器各自有边界。
- 提交语义明确：成功响应以 WAL commit frame 的 `fsync` 为界，不再用“已收到上游响应”代替记录成功。
- WAL 设计不是简单内存队列：有分片、commit frame、CRC、AEAD、checkpoint 和尾部恢复，能覆盖进程崩溃与掉电的差异。
- 时间语义、启动恢复、线程写入 actor、清理顺序和可见性 SLO 都有明确责任方，不是靠调用点补丁。
- 迁移章节明确最终删除旧同步路径和临时开关，没有把双写设计成长期结构。
- 候选尝试、图片流式、response state、failover 和现有记录入口都有映射，覆盖面完整。

## 主要问题

### WAL 写放大和首尾延迟仍未实测

**定性：建议优化（性能假设未验证）。**

当前设计已经把“降低总磁盘写入量”列为非目标，这是正确的，但也意味着不能把“移出请求路径”直接等同于“服务端压力更小”。WAL 保存完整内容后，物化器还要写入线程 JSONL，并多一次加密/解密；非流式响应仍要等 `TurnCompleted` 的 WAL 写入和组 `fsync`，流式首块仍要等 `TurnStarted` 提交，终止事件仍要等 `TurnFinished` 提交。

设计中的基线门禁和大 payload 压测是必要入口，但在没有实测数据前，不能承诺以下场景一定改善：

- 超大请求或长输出，WAL 内容写入本身成为首块或尾延迟的主要部分。
- 低并发，组提交无法摊销 `fsync`，每个请求仍要等一次提交。
- 磁盘吞吐、IOPS 或容器卷限流已经是当前瓶颈，双写会放大总 I/O。

建议在实现前执行设计中的基线门禁：用小/大 payload、流式/非流式、低/高并发分别测量 `storage_ms`、`wal_append_ms`、`wal_fsync_ms`、首字节、尾延迟、WAL 字节和写入线程 JSONL 的字节。若 WAL 提交成为新的 p99 大头，应停止完整实现，改为更轻的持久化方案，而不是继续扩大 WAL。

### 当前部署清单尚未同步 WAL 持久卷

**定性：违反项目已确认部署约束（实施前置条件）。**

设计已经明确 `RECORDING_JOURNAL_DIR` 和 `ACTIVITY_ROLLOUT_DIR` 必须位于持久卷，但当前 `deploy/docker-compose.yml:13` 只挂载了 `./data/sessions:/app/data/sessions`，README 也只记录 `ACTIVITY_ROLLOUT_DIR`。如果实现只增加 Rust 环境变量解析而不修改 compose/README，WAL 会落在容器临时层，容器重建后核心持久化承诺失效。

这不是设计歧义，而是实现顺序问题：**必须在同一个实现批次中增加 `./data/recording:/app/data/recording`、`RECORDING_JOURNAL_DIR`、UID 1000 目录权限、备份/升级说明和 README 环境变量表。** 在部署验收前，不能宣称“掉电/重启不丢记录”已经成立。

### materialization lag SLO 是产品假设

**定性：规范缺失导致风险。**

设计默认 `RECORDING_MATERIALIZE_LAG_SLO_SECONDS=5`，允许成功响应后活动列表、统计和会话正文短暂滞后。这解决了内部最终一致，但产品是否接受“请求成功、dashboard 暂时没有该活动”尚未确认。若业务要求实时统计，5 秒 SLO 和当前“读取已物化数据”的读路径需要重新设计。

建议在实现前确认：

- dashboard 是否允许 5 秒延迟，还是需要 pending 摘要/本地缓存。
- 会话内容/审计查询在 pending 期间返回什么；不能静默返回旧内容。
- 超过 SLO 时是否只告警，还是影响健康检查、限流或客户端提示。

### 现有 async/blocking 和数据库时间接口需要实质改造

**定性：建议优化（实现风险）。**

设计已经给出每线程写入 actor，但当前 `RolloutStore::begin` 是异步接口并持有 `OwnedMutexGuard`，`RolloutWriter` 使用同步 `std::fs` 和 `BufWriter`；实现需要明确 guard/writer 的 `Send` 约束、locking 顺序和关闭行为。数据库侧也需要新增接受外部 `activity_id`、`started_at`、`finished_at` 的幂等接口；当前 `identity_activities.created_at` 和 `activity_rollouts.created_at/completed_at` 都在插入时取 `Utc::now()`，不能直接复用。

设计已经把这些列为目标，但实现风险仍然高于普通局部改动。建议先做一个线程 actor 原型，验证同线程并发、取消、超时、`spawn_blocking` 关闭和锁生命周期，再扩大到所有 `/v1` 路径。

### 自定义 WAL 的复杂度仍需要 go/no-go

**定性：建议优化（工程比例）。**

WAL 不是简单异步任务，而是新的本地存储子系统：文件格式、分片、commit frame、AEAD、HKDF、checkpoint、恢复、每线程物化、response state locator 和容量控制。当前 `Cargo.toml` 已有 `aes-gcm` 和 `sha2`，但没有 `hkdf`；实现还要增加依赖、测试向量、密钥轮换和故障注入验证。

设计已经增加基线门禁，这是必要的。仍建议把完整 WAL 限制在“存储确实是 p99 显著组成部分”的前提下；否则先做更小的持久化改进，避免为一个未证实的瓶颈引入长期维护面。

## 整改优先级建议

### 先做基线和范围决策

- 按设计中的基线门禁测量小/大 payload、流式/非流式和不同并发。
- 计算 WAL 字节、JSONL 物化字节和写放大比例。
- 如果 `storage_ms` 不显著，或 WAL 写入成为新瓶颈，停止完整实现并回到更轻方案。

### 再落部署和产品边界

- 修改 `deploy/docker-compose.yml`、`.env` 示例和 README，增加 `data/recording` 持久卷、`RECORDING_JOURNAL_DIR`、目录权限和备份说明。
- 确认 5 秒 materialization lag SLO 和活动/统计/会话的 pending 读行为。
- 明确单实例写锁、克隆目录、多副本和多节点丢失边界。

### 最后进入实现批次

- 先做时间语义、RecoveryCoordinator 和线程 actor 的最小闭环。
- 接非流式，再接流式、图片、failover 候选和 response state。
- 完成延迟物化、崩溃、掉电、清理竞争、`fsync` 超时和真实 PostgreSQL 集成验证后，才删除旧同步路径。

## 评审边界

本次评审没有验证设计实现，也没有执行真实 PostgreSQL 集成测试、容器重启测试、掉电测试或真实上游压测。设计文档中的性能收益、恢复保证和部署行为仍需实现后按“验证”和“验收”章节重新取证。
