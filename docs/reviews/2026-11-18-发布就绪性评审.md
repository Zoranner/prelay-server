# Prelay 发布就绪性工程评审报告

> 本文的检查情况和主要问题记录的是 2026-11-18 整改前的评审基线。服务端整改完成后，当前状态见文末“整改记录”。

## 评审范围

本次评审对象是 Prelay 当前待发布版本，覆盖三个仓库自上次版本以来的提交：

- `prelay-server`：`v0.4.5..30e6394`，11 个提交
- `prelay-client`：`v0.2.4..84f0856`，4 个提交
- `prelay-protocol`：`427fe8a..057d877`，2 个提交

评审重点是工程体系、跨仓契约、数据库与部署变更、质量门禁和发布条件，不评价单个功能是否符合业务需求。服务端工作区还有 3 个未提交的 DeepSeek 基础指令改动，不属于本次提交范围，本文不把它们计入待发布内容。

## 评审依据

- `review-engineering` 通用工程基线
- `review-engineering` 的 Rust、Nuxt 专项清单
- 项目 `AGENTS.md`、README、部署说明和现有发布工作流
- 上次发布标签 `v0.4.5`、`v0.2.4` 及当前 `master` 提交
- 现有设计文档、实施计划和 2026-11-17 额度工程评审报告

## 总体结论

代码主线已经形成线性历史，三个仓库都只有 `master` 分支和单一工作树，主要质量门禁大部分通过。当前**不建议直接打新版本标签发布**，原因不是代码无法构建，而是发布元数据、服务端升级说明和共享额度的一致性边界还没有收口。

建议先把版本号与固定引用、服务端 WAL 备份说明、共享额度预留语义和客户端测试稳定性处理完，再进入发布候选。真实上游额度、PostgreSQL 集成测试和多实例行为仍需以部署环境或 CI 结果为准。

## 主要问题

### 版本号与固定引用没有更新

定性：违反项目已确认规范，发布阻断。

服务端仍是 `0.4.5`，客户端仍是 `0.2.4`。两边发布工作流都会校验标签版本与仓库版本完全相等，因此直接创建新标签会被 `prepare` 阶段拒绝。

证据：

- `prelay-server/Cargo.toml:3` 为 `0.4.5`
- `prelay-server/deploy/docker-compose.yml:3` 固定拉取 `0.4.5`
- `prelay-server/README.md:89` 仍写固定拉取 `0.4.5`
- `prelay-client/package.json:4`、`src-tauri/Cargo.toml:3`、`src-tauri/tauri.conf.json:4` 均为 `0.2.4`
- 服务端发布工作流要求标签版本等于 `Cargo.toml` 版本；客户端要求等于 `package.json`、`src-tauri/Cargo.toml` 和 `tauri.conf.json`

风险：标签工作流会在准备阶段失败，或者 Compose 用户继续拉取旧镜像，无法获得本批新功能。

建议：先确定新版本号，同步服务端 `Cargo.toml`、`Cargo.lock`、Compose、README，以及客户端三处版本和锁文件；再重新执行质量门禁。

### 服务端发布说明遗漏 WAL 目录

定性：违反项目已确认规范，存在数据风险。

发布工作流的 Release 正文仍只要求备份 PostgreSQL 和 `ACTIVITY_ROLLOUT_DIR`，没有提到本批新增的 `RECORDING_JOURNAL_DIR`。当前 README 明确说明 WAL 是物化完成前的权威记录来源，必须与活动 JSONL 一起备份。

证据：

- `prelay-server/.github/workflows/release.yml:182-185` 的发布正文只写了 PostgreSQL 与 `ACTIVITY_ROLLOUT_DIR`
- `prelay-server/README.md:83` 要求同时备份 `RECORDING_JOURNAL_DIR`
- `prelay-server/deploy/docker-compose.yml:14` 新增 `/app/data/recording` 持久卷
- `prelay-server/Dockerfile:20` 以 UID 1000 的 `relay` 用户运行

风险：用户按 Release 说明升级时可能不备份 WAL；已有部署新增 `./data/recording` 卷时，如果目录由 Docker 以 root 创建而容器用户不可写，服务会在启动阶段失败。

建议：更新 Release 正文和升级说明，明确创建并授权 `deploy/data/recording`，并写明 WAL 未排空时不能单独恢复旧备份。

### 共享额度预留没有结算，异步物化窗口可能穿透限额

定性：违反已确认的共享额度行为。

请求进入时按估算 token 预留，但响应体结束后 `ReservationGuard` 只释放预留；实际已用额度要等后台物化写入 `identity_activities` 后才能被下一次查询看到。物化间隔默认 100 毫秒，SLO 为 5 秒，连续请求可能在活动尚未物化时按旧读数通过。

此外，预留估算只使用请求体字节数（`estimate_tokens`），没有把最大输出 token 或图片等无 token 活动计入，单请求可能超过预留量。

证据：

- `prelay-server/src/service/quota/reservation.rs:147` 的 `Drop` 只释放预留
- `prelay-server/src/store/storage/provider_quota.rs:54` 的已用额度来自 `identity_activities`
- `prelay-server/src/service/recording/runtime.rs:123` 的物化循环按配置间隔运行
- `prelay-server/src/service/quota/reservation.rs:169` 按请求体字节估算 token

风险：共享限额可能被短窗口并发请求穿透，也会出现“刚用完仍显示有剩余”的读数。若产品接受最终一致，需要在发布说明中明确；若不接受，需要把预留结算到物化完成，或在内存中保留待物化的已用额度。

### 额度查询超时绕过上次成功读数

定性：违反已确认的额度查询行为。

适配器返回的错误会走缓存和上次成功读数逻辑，但外层 4 秒超时直接返回 `Unreachable`，不会进入 `snapshot` 的 `last_good` 回退。上游变慢时，列表可能显示“查询失败”，而不是 README/设计要求的旧读数。

证据：

- `prelay-server/src/service/quota/mod.rs:183` 的 `external_with_timeout` 超时直接构造错误
- `prelay-server/src/service/quota/mod.rs` 的 `snapshot` 只在适配器返回错误时尝试 `last_good`

风险：上游短暂超时会放大为前端额度列错误状态，且超时结果没有按错误 TTL 缓存，列表刷新会重复等待。

建议：把超时错误统一送入 `snapshot` 的错误处理和 `last_good` 回退路径，或让适配器内部超时返回可缓存的错误。

### 客户端并行测试不稳定

定性：违反硬性工程基线，影响发布门禁可信度。

客户端 Rust 测试默认并行运行时出现两个不同的单测失败，串行复跑均通过；串行运行 159 项全部通过。失败点分别是 Windows 文件锁子进程测试和 Windows 命令版本探测超时测试。

证据：

- `prelay-client/src-tauri/tests/credential_store.rs:147` 的独立进程文件锁测试
- `prelay-client/src-tauri/src/agents/tests/discovery.rs:103` 的 5 秒命令探测测试
- 两次默认并行运行的失败测试不同，串行运行全部通过

风险：发布工作流在 CI 中并行执行 `cargo test --all-targets --all-features`，可能出现与代码无关的红灯，导致发布流程不稳定。该问题不是本批提交引入，但会直接影响发布判断。

建议：让这些测试使用独立临时资源、放宽固定时序依赖，或在测试层面串行化需要独占文件锁/进程的用例。

### 客户端发布流程删除锁文件

定性：违反可复现构建基线。

客户端发布工作流在验证和构建阶段都先删除 `bun.lock`，再执行 `bun install`。本地和发布环境因此可能安装不同版本的依赖，本地通过不能证明发布产物使用同一依赖图。

证据：

- `prelay-client/.github/workflows/release.yml:45`、`:150` 的 `rm bun.lock`

建议：保留锁文件并使用 frozen lockfile 安装；如果确实需要刷新依赖，应在独立提交中更新锁文件并重新验证。

### 记录物化循环同步扫描整个 WAL 目录

定性：建议优化。

物化任务每个 tick 都递归读取整个 WAL 目录并累加文件大小，使用的是同步 `std::fs`，没有放入阻塞线程池。WAL 文件数量增长后，这会占用 Tokio worker，并可能反过来拉高物化延迟。

证据：

- `prelay-server/src/service/recording/runtime.rs:123` 的物化循环
- `prelay-server/src/service/recording/runtime.rs:432` 的 `directory_bytes` 递归扫描

建议：维护已写入/已清理字节计数器，或降低扫描频率并放入 `spawn_blocking`；在真实持久卷上做一次大目录基准。

## 待确认边界

- 非拥有者可以只读查看共享列表和额度；客户端已有 `readonly` 展示。需要确认这是产品预期的权限，不是误开放。
- 六个额度适配器只做了 fixture 验证，没有使用真实上游密钥验证。
- GoToken 没有公开额度接口，继续显示未接入；GLM 团队版不在范围。
- 共享额度预留是进程内状态，不支持多实例。
- 记录日志的真实持久卷、进程终止、掉电和 PostgreSQL 集成场景尚未在部署环境验证。
- 服务端工作区 3 个 DeepSeek 基础指令改动尚未提交，不能混入本次发布。

## 整改优先级建议

### 发布前

- 确定并同步新版本号，更新服务端 Compose/README 和客户端三处版本文件
- 更新 Release 正文，加入 `RECORDING_JOURNAL_DIR` 备份和目录授权说明
- 处理共享额度预留与异步物化的结算语义，或在发布说明中明确最终一致边界
- 修复额度超时未回退上次成功读数的问题
- 消除客户端并行测试不稳定，至少保证发布工作流的测试结果可重复
- 保留 `bun.lock` 并改为 frozen lockfile 安装
- 更新额度计划/评审文档的过期状态

### 发布环境

- 使用 CI PostgreSQL 跑完整的 `cargo test --all-targets --all-features`
- 构建并启动一次服务端镜像，验证 `data/recording` 权限、WAL 恢复和 `/health` 状态
- 用真实个人版 GLM 和其他供应商密钥验证额度接口和错误分类
