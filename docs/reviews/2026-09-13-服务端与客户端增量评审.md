## 主要问题

### 只检测到 ChatGPT 时，MCP 安装状态无法计算

定性：违反本次改动自己声明的安装目标契约，属于实现缺陷。

事实证据：

- `src-tauri/src/extensions/mcp.rs:29-34` 把 `ChatGpt` 与 `CodexCli` 映射到同一个 `McpHost::Codex`，安装时只写一次 `~/.codex` 配置。
- `src-tauri/src/extensions/catalog.rs:85` 在计算 MCP 状态前先执行 `mcp_agent_clients`（`catalog.rs:166-172`），该函数只保留 `CodexCli | OpenCode`，把 `ChatGpt` 过滤掉。
- `src-tauri/src/extensions/mcp.rs:147-199` 的 `mcp_installation_status` 在传入客户端列表为空时，循环不执行，`installed_clients` 为空，最终恒返回 `McpInstallAction::Install`。
- 客户端发现层把 ChatGPT 当作独立安装的客户端（`src-tauri/src/agents/integrations/chatgpt.rs:12-14`，按 Windows 应用包与卸载注册表判断），因此“只有 ChatGPT 桌面端、没有 `codex` CLI”是可达状态。

影响：这类机器上安装成功后，扩展列表仍显示“安装”，`installedClients` 为空，“补装”“已安装”永不出现；安装抽屉的客户端预选依赖 `installedClients`（`app/components/extensions/ExtensionInstallDrawer.vue:175-183`），同样算错。现有测试只覆盖同时传入两个客户端的情况（`src-tauri/src/extensions/mcp_tests.rs:271-281`）。

建议：状态计算应按安装目标去重而不是按客户端过滤，例如由 `clients.iter().map(mcp_host).collect::<BTreeSet<_>>()` 得到目标集合，报告时取一个已检测的客户端作为代表；同时补一条“只检测到 ChatGPT”的状态回归测试。

### 当前提交上前端 lint 门禁失败

定性：违反仓库验证门禁，属于实现缺陷。

事实证据：

- `bun run lint` 输出：`app/components/extensions/ExtensionInstallationScope.vue 5:7 error 'props' is assigned a value but never used @typescript-eslint/no-unused-vars`。
- 该文件未被未提交改动触碰（`git diff --quiet HEAD -- app/components/extensions/ExtensionInstallationScope.vue` 返回 0），`git show HEAD:` 内容与工作树一致，因此失败属于本次提交范围。
- 组件模板直接使用 `package`（`ExtensionInstallationScope.vue:13-15`），第 5 行的 `const props = defineProps<...>()` 没有使用点。

建议：去掉 `const props =`，或在模板中改为通过 `props.package` 取值；补跑 `bun run lint` 后再收口本次改动。

### MCP 清单安全规则在服务端与客户端逐字节重复

定性：违反“可复用职责不平行实现”的工程基线，属于结构问题。

事实证据：`prelay-server/src/extensions/mcp.rs:52-107` 与 `prelay-client/src-tauri/src/extensions/mcp_manifest.rs:71-118` 的六个谓词 `is_mcp_server_name`、`is_safe_http_url`、`command_has_plaintext_secret`、`is_sensitive_command_option`、`is_sensitive_name`、`is_environment_variable_name` 规范化比对后完全一致，唯一差异是服务端多了一个 `validate_environment_references` 包装函数；两边的保留服务名列表、敏感选项名单、URL 规则、环境变量命名规则都相同。

影响：同一条安全规则由两个仓库各自维护，任一侧单独调整都会造成“服务端放行而客户端拒绝”或反向的不对称；当前服务端校验尚未部署（`origin/master` 仍是 `v0.3.1`），客户端那份是唯一在生效的实现，漂移风险已经存在。协议仓已经是扩展 DTO 的唯一来源，规则本身却没有同源。

建议：把纯校验逻辑下沉到 `prelay-protocol`（例如 `extensions::validate_mcp_manifest`），两个仓库分别保留错误类型映射与执行点（服务端在分发安装包前，客户端在写入宿主配置前），既保持唯一来源，也保持双端强制。

### 明文凭据识别只覆盖选项名黑名单

定性：安全规则不完整，属于实现缺陷（影响面取决于扩展库的准入，当前为内部固定版本包）。

事实证据：`is_sensitive_command_option`（服务端 `mcp.rs:75-98`、客户端 `mcp_manifest.rs:94-117`）只按“参数去掉前导 `-` 后、`=` 之前的部分”匹配固定名单。以下形态都不会被拒绝：

- `--header=Authorization: Bearer <secret>`：选项名是 `header`，不在名单内。
- `mcp-remote https://host/path?token=<secret>`：位置参数不在选项位，且 HTTP 地址规则只作用于 `transport.http.url`，不作用于 stdio 参数。
- `--config=secret.json`、`--webhook https://user:pass@host`。

设计文档要求“命令参数中出现明文凭据选项”必须在写入前失败，因此这是实现与设计意图之间的差距。

建议：补齐 `header`、`authorization`、`bearer`、URL userinfo 与含 query 的位置参数形态；同时在文档中把该规则标注为启发式防护，避免把“已拒绝明文凭据”写成完备保证。

### 语言模型条目新增与下线：既有映射会静默失效

定性：新增与下线的产品变更已确认为预期（2026-09-14 用户确认）；遗留的是既有映射的处理方式和文档表述。

事实证据：

- `config/catalog/models/language.toml:165-166` 新增条目 `deepseek-flash`（展示名 `DeepSeek V4.1 Flash`，优先级 3）；`config/catalog/providers.toml` 的 deepseek `language_models` 同步删去 `deepseek-v4-flash-vision-exp`、加入 `deepseek-flash`。该提交的信息写的是“重命名 DeepSeek Flash 模型条目”，与实际语义（新增一条、下线一条）不一致。
- `src/routes/v1/models.rs:45-54` 在每次 `GET /v1/models` 时按目录过滤，`upstream_model` 不在目录中的映射不会返回。
- `src/storage/endpoint_validation.rs:66-79` 在保存接入点时用 `provider_supports_language_model` 校验，目录已不支持的模型名直接报错，错误文本为 `provider deepseek does not support catalog model deepseek-v4-flash-vision-exp`。
- `src/schema/provider_catalog.rs:112-137` 的 `provider_model_catalog_v2` 迁移带版本门控，只执行一次，不会为本次下线再次清理历史映射。

影响：既有接入点中指向 `deepseek-v4-flash-vision-exp` 的映射会从 `/v1/models` 消失；这类接入点再次保存会被拒绝，用户必须先删除该映射才能保存其他改动。`/v1` 请求路由本身不查目录，旧模型名仍会被转发到上游并以上游错误结束。

建议：下线已确认，不需要兼容旧 ID；为减少困惑，可在发布说明写明下线的模型 ID，或让客户端/管理端在模型不在目录时给出“该模型已下线，请重新选择”的提示，而不是笼统的校验失败。

### 第三方模型套用官方默认基础指令（已确认）并放大目录体积

定性：套用官方默认基础指令是预期行为（2026-09-14 用户确认）；此处只记录体量与一致性验证边界。

事实证据：

- `config/catalog/models/instructions/README.md` 说明模板来源为 `openai/codex` 仓库的 `model_messages.instructions_template` 与 `prompt.md`（版本 `rust-v0.153.4`），加载顺序为“条目显式值 > `<id>.md` > `_default.md`”。
- `src/provider_catalog/loading.rs:83-105` 实现该顺序，`config/catalog/models/instructions/_default.md` 会被 17 个语言模型中除 4 个 gpt 系列和 `MiniMax-M3` 之外的全部条目使用。
- 实测：17 个模型解析后的基础指令合计 325541 字符（约 318 KiB），其中 `gpt-5.6-sol.md`、`gpt-5.6-terra.md`、`gpt-5.6-luna.md` 各 17766 字节且内容相同；改动前这些条目基本是空的 `base_instructions`。
- 客户端把该字段写入本地模型档案：`src-tauri/src/agents/settings/codex_catalog.rs:74-77`、`codex.rs:241-254` 生成 `~/.codex/models.json`。

影响：`/api/catalog/models/language` 响应体量与客户端本地 `models.json` 从接近零增长到数百 KiB，属于已接受的行为变化；Kimi、GLM、DeepSeek、Qwen 等第三方模型会显式携带 OpenAI Codex 的默认基础指令。

建议：在 `config/catalog/models/instructions/README.md` 记一句响应体量与本地文件体量预期，便于后续排查体量异常。本次未核验模板与上游原文的逐字节一致性（README 的保真声明未独立验证）。

### MCP 抽屉收集的环境变量取值没有去向

定性：界面承诺与实现不一致，属于实现缺陷（设计文档已把它列为“当前未落实”）。
