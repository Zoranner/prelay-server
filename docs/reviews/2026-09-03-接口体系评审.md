# prelay-server 接口体系评审报告

## 评审范围

本次只评审服务端管理 API、`/v1` 协议入口、供应商与模型目录、鉴权边界、接口文档和验证状态，不评价具体上游模型效果，也不修改客户端或协议仓库。

## 评审依据

- 服务端 `AGENTS.md` 中的路由边界、鉴权和验证要求。
- `src/routes/api`、`src/routes/v1` 当前实现。
- `docs/architecture/provider-catalog.md` 与迁移计划中的目录契约。
- `README.md` 和 `crates/protocol/docs/protocol/` 中的接口清单。
- 当前 checkout 的 `cargo fmt`、Clippy 和全量测试结果。

## 总体结论

接口体系目前是“资源分组基本形成，目录命名已统一，管理契约仍有收敛项”。管理 API 的身份、供应商、接入点、统计、扩展、客户端更新和目录查询已经分开，目录配置已统一到 `deploy/app/config/catalog`，目录查询已统一到 `/api/catalog/*`，`/v1/models` 也已收敛为标准模型对象字段。供应商管理仍接受旧的自由配置模型，身份单复数和供应商动作路由仍需后续契约决策；完整测试与真实供应商、Docker、客户端联调仍未完成。

## 检查情况

- `cargo fmt --all -- --check`：通过。
- `cargo clippy --all-targets --all-features -- -D warnings`：通过。
- `cargo test --all-targets --all-features`：206 个单元/集成测试通过；`source_layout::source_rust_files_stay_within_limit` 失败，报告 `src/provider_catalog.rs` 770 行以及两个未改动文件超过 450 行限制。
- 已接入并验证认证管理接口 `/api/catalog/providers`、模型分类列表和详情接口。
- 未执行真实供应商、Docker 部署或客户端联调；本报告不把本地测试等同于端到端验收。

## 当前接口矩阵

### 管理 API

已实现身份注册与凭据轮换、供应商增删改查及连通性/协议测试、接入点增删改查及令牌重生成、统计、客户端更新、扩展目录，以及 `/api/catalog/*` 下的供应商和两类模型目录列表/详情接口。

### 协议 API

已实现 `GET /v1/models`、`POST /v1/responses`、`POST /v1/chat/completions`、`POST /v1/messages` 和 `POST /v1/images/generations`，统一使用 Endpoint Token 鉴权。

## 主要问题

### `/v1` 非标准图像模型列表已移除

定性：违反公开接口契约。

原有 `src/routes/v1/images/models.rs` 属于未挂载的非标准接口，现已删除；图像生成模型目录由 `/api/catalog/models/image-generation` 提供，`/v1` 只保留标准协议入口。

建议：保持当前边界，不恢复 `/v1/images/models`，并在协议材料中只记录标准 `/v1` 入口。

### 供应商管理 API 没有以供应商目录作为唯一事实源

定性：违反已确认的目录架构，优先级高。

`CreateProviderRequest` 和 `UpdateProviderRequest` 仍暴露 `provider_type`、`capabilities` 和 `models`（`crates/protocol/src/providers.rs:131-149`）；`POST /api/providers` 直接将请求交给存储层（`src/routes/api/providers.rs:42-57`），存储层直接保存这些值（`src/storage/providers.rs:99-137`），没有通过 `ProviderCatalog` 校验供应商、模型、协议和协议 URL。

这与目录文档要求的“服务端目录驱动认证、协议和模型”以及迁移计划中“管理 API 不接受自由协议、模型或认证方式”的目标不一致（`docs/superpowers/plans/2026-09-02-provider-catalog-server-migration.md:380-395`）。当前系统可能出现数据库中存在目录外供应商或模型，随后只能在 `/v1/models` 过滤阶段被静默排除。

建议：下一阶段先收敛服务端管理 API 的领域契约和校验入口，再同步协议仓和客户端；本轮不应通过局部字段兼容继续维持两套配置事实源。

### `/v1/models` 标准字段已收敛

定性：违反服务端质量门禁，优先级中高。

`src/routes/v1/models.rs` 现只返回 OpenAI 标准模型对象字段 `id`、`object`、`created` 和 `owned_by`，并过滤图像生成模型。原有 3 个失败夹具已改为使用当前目录中的语言模型，相关单元测试通过。

建议：继续以标准字段维护该接口；`created` 当前无目录事实来源，使用固定的 `0` 表示未知，后续若要提供真实时间需先扩展目录契约。

### 接口清单与实现存在文档漂移

定性：规范缺失导致风险，优先级中。

README 已补充 `/api/catalog/*` 和新的 catalog 配置目录；协议 Bruno 集合仍未补充目录接口请求文件。

建议：在接口契约稳定后维护一份服务端接口矩阵，并同步 README、架构文档和协议材料；文档应明确每个入口的认证方式、请求/响应 DTO、错误语义和是否支持流式。

### 模型发现接口与目录迁移目标冲突

定性：契约漂移，优先级中，需在下一阶段决策。

服务端仍注册 `POST /api/providers/discover-models`（`src/routes/api/providers.rs:23-27`），并保留 `model_discovery` 实现；迁移计划明确要求删除模型发现路由和 DTO，改由静态供应商目录提供模型集合（`docs/superpowers/plans/2026-09-02-provider-catalog-server-migration.md:380-395`）。

建议：在管理 API 重构阶段明确保留或删除。若目录作为唯一事实源，应删除该接口及其协议材料，避免客户端继续把上游 `/models` 响应当作可配置模型来源。

### 源码文件超过项目行数门禁

定性：违反服务端质量门禁，优先级中。

完整测试中的 `source_layout::source_rust_files_stay_within_limit` 报告三个文件超过 450 行：`src/provider_catalog.rs` 770 行、`src/bridge/stream/decode/chat.rs` 595 行、`src/providers/chat_completions/mod.rs` 468 行。前两个超长文件不是本次目录接口改动新增，`provider_catalog.rs` 是当前目录加载、解析、校验和响应转换的集中实现，已经承担多个职责。

建议：后续将目录加载、模型校验、供应商校验和 DTO 转换拆为独立模块，先处理 `provider_catalog.rs`；另外两个文件单独安排结构拆分，不在本次接口契约提交中混入。

### 管理 API 二级路由命名尚未完全统一

定性：规范缺失导致风险，优先级中。

当前二级路由大部分采用资源复数名，例如 `/api/providers`、`/api/endpoints`、`/api/extensions` 和 `/api/stats`，资源详情也统一使用 `/{id}` 形式，整体方向是成体系的。但仍存在三类明显不一致：

- 身份集合使用 `/api/identities`，当前身份和凭据操作却使用单数 `/api/identity` 与 `/api/identity/credential/rotate`（`src/routes/api/mod.rs:26-36`）；
- 用户配置供应商使用 `/api/providers`，静态供应商目录现已统一到 `/api/catalog/providers`（`src/routes/api/providers.rs:23-32`、`src/routes/api/catalog.rs:11-26`），两者职责和命名空间已分离；
- `/api/providers/discover-models`、`/api/providers/test-protocol`、`/api/providers/{provider_id}/ping` 将动作动词直接放入资源路径，且前两者是集合级动作、后者是单资源动作，表达方式不一致（`src/routes/api/providers.rs:25-28`）。

建议保留面向身份、实际配置和运维统计的现有资源分组。静态目录前缀已统一为 `/api/catalog/providers`、`/api/catalog/models/language` 和 `/api/catalog/models/image-generation`，并提供对应详情路由。身份相关路径仍应在后续契约调整时明确采用“集合 `/identities` + 当前身份 `/identity`”还是统一为单一资源语义；供应商动作接口则应逐项确认是否保留，避免继续扩展新的动词路由。

## 整改优先级建议

### 第一优先级：保持公开接口边界

- 保持已删除的 `/v1/images/models` 不再恢复。
- 保持 `/v1/models` 的标准字段，不再向 `/v1` 添加目录专有字段。

### 第二优先级：收敛供应商配置契约

- 以 `ProviderCatalog` 校验供应商、模型、协议和 URL。
- 删除或替换 `provider_type`、自由 `capabilities`、自由 `models` 这套旧管理输入；涉及共享 DTO 时先在协议仓完成。

### 第三优先级：统一管理 API 命名空间

- 已将静态供应商和模型目录统一迁移到 `/api/catalog/*`，不再使用 `/api/provider-catalog`。
- 保持 `/v1/*` 只承载标准协议，不把目录查询或管理动作放入 `/v1`。
- 对身份单数/复数语义和供应商动作路由做一次契约决策，再同步实现、协议材料和客户端调用。

### 第四优先级：同步接口材料

- 补齐 README、架构文档和 Bruno 接口集合。
- 对模型发现接口做最终取舍，并确保实现、DTO、文档和客户端调用保持同一结论。
