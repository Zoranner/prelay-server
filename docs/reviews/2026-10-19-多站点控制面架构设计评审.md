# Prelay 多站点控制面与网关架构设计评审

## 评审范围

评审对象为 `docs/superpowers/specs/2026-10-19-multi-site-control-plane-design.md`。

评审覆盖控制面/网关职责、三站点部署、Provider 一次性配置、身份与令牌、配置分发、用量统计、客户端、故障、安全和迁移。

本次只做设计评审，不修改代码，不执行部署。

## 总体结论

架构保持上一版确认的边界，没有退回三套完整单体：

- 1 个 `prelay-control` + 3 个 `prelay-gateway` + 4 个独立 PostgreSQL。
- 控制面在总部管理区，通过私网/VPN 连接三个网关；公网网关是唯一互联网 LLM 入口。
- 全局 Provider/Endpoint、KMS 主副本 + 站点信封、签名 Endpoint Token、配置快照、`site_epoch`、OIDC 一中心三网关都保留。
- Provider 只在控制面配置一次，站点通过配置快照获得元数据和本站信封，不再重复配置三次。

上一轮把“简洁”误做成“推翻架构”，删除控制面/网关并改成三套单体，这是错误的。本版已恢复架构；简化只体现在文档表达和去重复，不改变边界。

## Provider 一次性配置

这是本次评审最关键的收敛点。

- 控制面维护唯一 Provider 实体，Provider 创建者填写一次 API Key。
- 控制面用 KMS 主密钥保存主副本，为每个启用站点生成公钥信封。
- 网关配置快照只包含本站信封；网关本地解封，明文不落盘。
- Endpoint 和模型路由也由控制面统一维护，站点只用站点策略过滤。
- Endpoint Token 仍按站点签发，客户端 profiles 自动获取。

因此不再存在“同一 Provider 在三个站点各配一次”的问题，也没有引入第二套共享 Provider 目录。

产品里没有管理员角色，只有用户。Provider/Endpoint 的所有者是创建它的用户；其他用户按 `private`/`selected`/`all` 分享关系只读使用 Provider，不接触密钥。站点注册和证书轮换是部署动作，不是产品角色；审计日志由部署方按基础设施权限访问，不作为应用角色。

Endpoint 当前按设备身份归属；同一人员的多台设备不会自动合并 Endpoint。OIDC 只用于人员统计和身份识别，不自动合并设备 Endpoint。Provider/Endpoint 名称在所有者范围内唯一，不同用户可以重名。

## 清晰性

主链路清楚：

```text
控制面配置 -> 站点配置快照 -> 网关本地缓存 -> 上游调用
网关活动 -> outbox -> 控制面 usage_facts -> 团队统计
客户端 profile -> 本站网关 -> Agent 配置
```

Provider、Endpoint、Token、配置、用量各自只有一个事实来源：

- Provider/Endpoint/Token 签发：控制面。
- LLM 执行和本地活动：网关。
- 团队统计：控制面 `usage_facts`。
- 客户端站点选择：客户端 profiles。

统计口径已收敛为 `personal` 和 `team`，与现有 `ModelStatsScope` 一致；不新增 `site`/`global` scope。`site_id` 只用于数据归属和幂等，不作为统计维度。OIDC 前 `team` 按设备身份聚合，OIDC 后按 `person_id` 合并同一人员的多设备。

## 简洁性

文档比上一版压缩了重复说明，但保留以下必要边界：

- 控制面/网关拆分。
- 4 个独立数据库。
- KMS 主副本 + 站点信封。
- 按站点签名 Token。
- 配置快照、租约和 last known good。
- `site_epoch + site_seq` 重放。
- OIDC provider 选择、JWKS 和 `person_id`。

这些不是装饰性复杂度，而是“Provider 只配置一次、站点本地自治、团队统计、站点隔离”四个目标的直接结果。把它们删掉会退回三套单体，违背已确认架构。

## 阻断项与前置条件

### 项目规则需要同步

- 根 `AGENTS.md` 仍规定 Provider Key 仅以单一 `ENCRYPTION_KEY` 保存；设计改为 KMS 主副本 + 站点信封。
- `prelay-server/AGENTS.md` 仍描述单实例服务；设计拆为控制面/网关。
- `prelay-client/AGENTS.md` 需要允许多个站点 profile 和站点目录，但继续保持客户端不直接转发 AI 请求。

规则变更需要单独评审，不能混进功能提交。

### 网络与密钥前置条件

- 总部管理区、三个站点之间需要私网/VPN/专线连通。
- 控制面需要 KMS/Vault；站点需要本地 KMS/TPM 或等效密钥存储。
- 公网网关是唯一互联网入口，控制面不直接暴露。

### OIDC 前置条件

- 三个 OIDC 网关需要共享逻辑 issuer，或提供稳定 `person_id` claim。
- 控制面需要访问三个 OIDC 接入点的 discovery/device/token/JWKS 端点；否则需要确认降级代理路径。
- IdP 需要支持设备授权流程。

### 迁移前置条件

- 旧 `ENCRYPTION_KEY` 必须可用，用于一次性解密现有 Provider Key。
- 现有 Endpoint Token 需要重签，客户端 Agent 配置需要更新。
- 需要停机或只读窗口，以及迁移后的统计对账。

## 剩余风险

- KMS/HSM 和控制面被攻破的残余风险仍需通过权限分离、审计和轮换控制。
- 配置租约和 Token 有效期默认 7 天，需要按业务中断容忍度校准。
- 30 天 outbox 重放窗口是硬边界，超出后无法自动补齐。
- 控制面仍是配置和团队统计的单点；网关本地推理不受影响。
- 全局 Provider/Endpoint 的迁移和所有权/分享模型需要实际实现验证。
- Provider 所有者离职或身份删除后的转移规则需要产品确认；当前只允许所有者转移或自动禁用，不引入管理员接管。
- 客户端切换 profile 后，运行中的 Agent 可能需要重启。
- OIDC 一中心三网关的人员键契约需要 OIDC 团队确认。

## 验证情况

本轮是静态设计评审，未执行代码测试、数据库迁移、Docker 部署、VPN/KMS/OIDC 联调或真实上游调用。

已执行的低成本检查：

- 设计文档 LF 行尾，无 CRLF。
- 标题未使用序号。
- 未发现疑似真实 Token、Bearer 凭据或 `sk-` 形式的密钥。
- `git -C prelay-server diff --check` 通过。
- `prelay-server` 工作区原有 `M deploy/.env.example` 未被修改。

## 结论

当前设计恢复了已确认的控制面/网关架构，并用控制面的全局 Provider/Endpoint 目录解决了“Provider 配三次”的问题。

后续只做文档精简，不再动架构边界；如果确实需要简化，应先明确是删重复说明、删冗余状态，还是改变架构，三者不能混为一谈。
