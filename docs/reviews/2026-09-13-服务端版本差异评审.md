## 评审范围

- 本机执行的格式、Clippy 和定向测试命令及其输出。

## 总体结论

MCP 清单校验的方向正确：清单在固定版本下发前被校验，只接受可表达的 stdio / HTTP 配置，拒绝工作目录、明文凭据、带 query 或内嵌凭据的地址与不同名的环境变量引用，并且服务端与客户端各自校验一次。校验函数测试覆盖了全部拒绝分支。

基础指令模板的加载优先级（显式配置 > `<模型 id>.md` > `_default.md`）实现与文档一致，并有 6 项定向测试。但这一改动同时把「模型基础指令」的事实来源从本机 Codex CLI 版本移到了服务端目录，且部署步骤、发布说明和上游同步机制都还没有跟上。

本机执行的格式、Clippy、`provider_catalog` 与 `extensions` 定向测试全部通过，未发现阻断发布的服务端问题；需要处理的是诊断能力、部署同步和跨版本影响说明。

## 主要问题

### MCP 清单被拒绝时无法定位原因（重要）

`src/extensions/mcp.rs` 中覆盖服务名、保留名、空命令、工作目录、`enabled`、明文凭据、URL 结构、请求头名称、环境变量引用共 12 处判定，全部返回 `CatalogError::ContentInvalid`；该错误在 `src/routes/api/extensions.rs:99-100` 被映射为 `ExtensionContentInvalid` / “扩展内容无效”，服务端也不记录具体判定。

后果是扩展包作者和运维无法区分「服务名撞上保留字」和「URL 带了 query」，也无法从响应或日志反推清单哪一条不合格，与仓库「性质不同的失败不应压缩成同一个笼统错误」的要求冲突。

建议按判定大类给出可区分的稳定错误码或脱敏日志，例如服务名、传输配置、凭据表达、环境变量引用四类。

### 基础指令的事实来源从 Codex CLI 迁到服务端目录，长期策略未明确（重要）

`src/provider_catalog/loading.rs:81-115` 的 `resolve_base_instructions` 在条目未显式配置时读取 `models/instructions/<id>.md`，再回落到 `_default.md`；`config/catalog/models/language.toml` 中条目的 `base_instructions = ""` 被删除，因此没有专属模板的模型（kimi、glm、deepseek 等）现在会拿到 `_default.md` 的 20 751 字符 Codex CLI 默认提示。

客户端会把该值原样写入 `~/.codex/models.json`（`prelay-client/src-tauri/src/agents/settings/codex_catalog.rs:74-77`），因此服务端目录成为这些模型基础指令的唯一来源，`gpt-5.6-luna/terra/sol`、`gpt-6-astra` 更是固定为 `rust-v0.153.4` 的原文。

需要确认的边界：

- Codex 升级后模板不会自动更新，`config/catalog/models/instructions/README.md` 只写了人工同步流程，没有版本锚点、接口字段或漂移检测；
- `tests/provider_catalog.rs` 的 `deployment_catalog_fills_official_instructions_from_files` 只断言前缀和长度大于 10 000，无法发现内容过期。

建议在目录或接口中记录模板来源版本，并明确「以服务端目录为准」是否为长期策略；否则应恢复空指令让客户端沿用本机 Codex 版本。

### 部署步骤没有同步新目录（重要）

`Dockerfile` 只把 `src`、`Cargo.toml`、`Cargo.lock`、`build.rs` 和协议 crate 打进镜像，目录配置由 `deploy/docker-compose.yml:13` 以只读方式挂载 `./app/config`，但 `README.md:83` 仍写“目录内必须包含 `providers.toml` 和 `models/` 下的两类模型文件”，没有提到 `models/instructions/`。

只同步 toml 文件的部署会静默退化为「没有基础指令」，而文档、README 和测试都假定模板存在。建议把 `models/instructions/` 写入部署步骤，并在加载时对「模板目录缺失」给出一次可观测的提示。

### 模型标识重命名对已安装客户端的影响未说明（重要）

`deepseek-v4-flash-vision-exp` 被重命名为 `deepseek-flash`（`config/catalog/models/language.toml`、`config/catalog/providers.toml`）。模型 `id` 同时是上游模型名，重命名本身与 DeepSeek 公开文档一致（文档同时列出 `deepseek-flash` 与旧名，见 `https://api-docs.deepseek.com/quick_start/pricing`）。

但客户端只在保存设置时校验默认模型是否属于当前目录（`prelay-client/src-tauri/src/agents/settings/codex.rs:135`、`218-239`），校验失败会直接报“默认模型不属于所选接入点。”并且不会自动改写用户 `config.toml` 里的 `model`。目录先于客户端更新时，已选择旧模型标识的用户会在保存设置时被阻断，需要人工改选。建议在发布说明中写明，或让客户端在检测到目录中已消失的默认模型时给出可执行的修复路径。

## 次要问题

### 清单校验的边界需要写明

- `is_safe_http_url`（`src/extensions/mcp.rs:47-60`）允许 `http://`。如果是有意为内网 MCP 放行，建议在清单规范里写明；否则明文传输与对 stdio 凭据的严格校验并不对称。
- `command_has_plaintext_secret`（`src/extensions/mcp.rs:62-96`）是名称白名单，无法识别 `sh -c "curl -H 'Authorization: Bearer xxx'"`、`--header`、`--api-key-file <路径>` 这类参数；这是可接受的残余风险，但检测边界目前只能从测试推断。
- 启动命令本身不校验可移植性：`command[0]` 可以是 `C:\tools\tool.exe` 或含用户目录的绝对路径，与 `2af8015` 提交说明中的“不可移植字段”不完全一致（实际只拒绝了 `cwd`）。
- `resolve_base_instructions` 用模型 id 拼接文件名（`loading.rs:88`）。当前模型 id 来自自维护目录，风险很低；如果将来允许外部来源提供模型 id，需要补路径校验。

### 文档字符数误差

`config/catalog/models/instructions/README.md` 把 `MiniMax-M3.md` 记为 137 字符，实测为 138（含末尾换行），其余文件按含换行计。

## 剩余边界

- 本轮结论只覆盖服务端已提交的 9 个提交；`v0.3.1` 之后没有版本号变更，`deploy/docker-compose.yml` 仍固定 `ghcr.io/zoranner/prelay-server:0.3.1`，发布流程尚未启动。
- 服务端 MCP 校验收紧尚未部署，`prelay-client/docs/superpowers/specs/2026-09-12-mcp-extension-installation-design.md:354` 已把这一点记为未落实事项。
