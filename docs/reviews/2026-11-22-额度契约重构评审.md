## 评审范围

本次评审 2026-11-22 的额度契约重构，范围包括：

- `prelay-protocol` 的额度 DTO 和序列化契约。

评审只判断工程实现、接口边界和验证证据，不评价真实供应商接口可用性、视觉喜好或尚未确认的产品需求。

## 总体结论

重构方向成立：协议从展示字符串改为语义窗口，服务端适配器按窗口类型输出，客户端集中决定文案和环位，共享额度的日窗口与累积窗口也和套餐窗口分开。当前代码的协议测试、额度定向测试、客户端全量测试、类型检查和 lint 均通过。

当前不建议直接进入发布。数据库集成测试仍按旧额度字段断言，带 `TEST_POSTGRES_URL` 的测试会失败；共享额度的实际结转计算缺少直接覆盖；Kimi 的 `limits[]` 解析在参考实现支持的 `detail` 缺失形态下会丢窗口。

## 主要问题

### 数据库集成测试仍按旧额度契约断言

定性：高，违反硬性工程基线。

`tests/management/provider_sharing/quota.rs:75-78` 仍断言 `label`、字符串形式的 `limit` 和 `amount`：

```text
windows[0].label == "1 天"
windows[0].limit == "1000"
windows[0].amount == "1000"
```

同一文件 `:269-270` 仍断言字符串形式的 `limit` 和 `amount`。新协议已经删除 `label` 和 `amount`，并把共享额度的 `limit`、`remaining` 改为数值字段，因此这些用例在有测试数据库时会失败。

这是契约迁移没有覆盖测试夹具，不是旧客户端兼容问题。`cargo test --lib service::quota` 只运行库内额度测试，`cargo clippy --all-targets` 只编译集成测试，两者都不会暴露这些运行时断言失败。

建议在合并前把所有相关集成测试改为断言 `kind`、数值 `limit`、`remaining` 和 `unit`，并在测试数据库中实际运行。

### 共享额度的结转计算缺少直接验证

定性：中，验证覆盖不足。

共享额度的周期边界测试仍在 `src/service/quota/shared.rs:318-387`，覆盖日、周、月边界和上一周期边界；但真正负责读取用量、计算结转、组装窗口的 `windows()` 在 `src/service/quota/shared.rs:12-80`，没有直接用例。

现有数据库集成测试的共享额度用例使用 `accumulate: true`，但没有构造上一周期的使用记录，因此无法证明“上一篇剩余额度进入今天”的行为。当前绿色结果只能证明周期数学和窗口类型，不能证明结转结果。

建议增加一个不依赖真实上游、但覆盖 `windows()` 输入的用例，或至少扩展共享额度集成测试：上一周期有使用记录时，验证日窗口的 `remaining`、`limit` 和 `used_percent`。

### Kimi `limits[]` 缺少 `detail` 时会丢窗口

定性：中，兼容边界缺口。

`src/service/quota/adapter/kimi.rs:31-33` 使用：

```text
let detail = limit.get("detail").unwrap_or(limit);
```

参考实现 `../.refs/magpie/internal/provider/planquota.go:501-503` 的处理是：优先 `detail`，缺失时退回 `window`。当前代码在 `detail` 缺失或为 `null` 时退回外层 `limit`，外层通常没有 `limit`、`used` 或 `remaining`，结果会静默跳过该窗口。

这会直接影响 Kimi 的 5 小时或其他动态窗口读数，且解析失败不会报错，只会表现为窗口缺失。建议按参考实现改为 `detail` 缺失时取 `window`，并补充 `detail` 缺失、`detail: null` 两种 fixture。

### 额度不足的 429 诊断仍混合服务端拼接文本和内部枚举

定性：低，建议优化。

`src/service/quota/reservation.rs:187-192` 的错误消息：

```text
共享额度不足：{:?} 窗口可用 {} tokens，重置 {}
```

`{:?}` 会输出 `Day`、`Week` 这类 Rust 枚举调试名，和中文消息混在一起。该消息仍由服务端拼接，客户端无法按窗口类型统一生成文案；这与本次“服务端只算数据、客户端决定文案”的方向不一致。

这不是本次重构的功能阻断项，且计划明确把共享额度 429 错误码改造留到后续。但在统一模型后，至少应避免把内部枚举调试名暴露给用户；后续可改为稳定的错误参数，由客户端生成窗口文案。

## 整改优先级建议

### 合并前

- 更新 `tests/management/provider_sharing/quota.rs` 的旧字段断言，补上 `remaining`、`unit` 和数值 `limit`。
- 用 `TEST_POSTGRES_URL` 运行 `cargo test --test management`，确认共享额度集成测试通过。
- 为 Kimi `limits[]` 增加 `detail` 缺失和 `detail: null` 的解析用例，并修正回退对象。

### 发布前

- 为共享额度增加结转行为测试，覆盖上一周期有剩余、上一周期已用尽、共享建立时间晚于上一周期起点三种情况。
- 明确三仓版本策略。当前协议、服务端和客户端都还没有新的发布版本号；如果发布这次不兼容契约，应先确定版本递增和发布顺序。
- 协议提交目前仍只在本地领先远端，父仓 submodule 指针都指向 `736bf40`。推送前先发布协议提交，再更新父仓远端，避免克隆父仓时找不到 submodule commit。
- 用真实 Kimi、GLM、MiniMax、Command Code 和 OpenCode 响应做一次额度列快速验证，重点检查月窗口、余额和缺失窗口的展示。

### 后续

- 把共享额度 429 改成稳定错误码和结构化参数，由客户端生成窗口文案。
- 为 `QuotaRings` 和两类额度单元格增加真实渲染或组件级交互测试，补充当前只有源码断言和视图模型单测的边界。

## 剩余边界

- 本次没有连接真实供应商接口，适配器测试全部使用契约 fixture。
- 本次没有启动 Tauri 客户端观察额度列的真实布局、tooltip 和窄列表现。
- 服务端数据库集成测试因缺少 `TEST_POSTGRES_URL` 未执行；报告中的集成测试问题来自静态代码证据，不是运行结果。
- 共享额度预留仍是进程内状态，不跨服务实例共享。
