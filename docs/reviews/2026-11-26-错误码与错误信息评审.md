# Prelay 错误码与错误信息工程评审报告

## 评审范围

本次评审对象是 `provider-relay` 协调目录下三个独立仓库的错误码与错误信息契约：`prelay-protocol`（管理 DTO 与稳定错误码的唯一来源）、`prelay-server`（`/api/*` 与 `/v1/*` 两个响应面）、`prelay-client`（Tauri + Nuxt 桌面端）。只评审错误码登记、错误响应形状、message 语义与语言、客户端取码和文案映射，不评价功能需求完成度、业务规则正确性或单个交互 bug。

报告落在 `prelay-server/docs/reviews/`，因为协调目录本身不是 Git 仓库；该仓已有跨仓评审先例（`2026-09-13-服务端与客户端增量评审.md`）。

评审基线是当前工作树，包含未提交的共享额度重构。本轮整改只在错误契约相关文件中进行；额度重构、分享抽屉和未提交基线没有被回退或覆盖。整改结果已合并进本报告，不另设复评章节。

## 评审依据

- 用户确认的六条规则：服务端只返回稳定错误码；message 只给开发排障；单条 message 单语且不夹带机器标识；`/api/*` 用 `{"error":{"code","message"}}` 且 code 来自 `ProtocolErrorCode`；`/v1/*` 用 OpenAI 错误体；客户端只有一个码到文案的映射，未识别码才兜底。
- 工作区 `AGENTS.md`：三仓独立提交；管理 DTO、错误码和序列化契约先改 `prelay-protocol`；设备凭据、Endpoint Token 与 Provider API Key 不得进入文档、夹具、客户端状态或日志。
- `review-engineering` 通用工程基线、`stacks/rust.md`（错误处理、类型边界和 API 契约）、`stacks/nuxt.md`（utils 职责、文案归属）。
- 仓库内既有规范：`prelay-protocol/src/error.rs` 对错误响应体的注释、`docs/superpowers/specs/2026-10-30-responses-state-protocol.md` 的 `/v1` 错误体、`docs/superpowers/specs/2026-11-17-quota-design.md` 的 `shared_quota_exhausted` 约定。

## 总体结论

用户规则 1 至 6 在 `/api` 与 `/v1` 两个响应面已经成立，本轮整改关闭了首轮评审的全部高、中优先级问题。

`/api` 的所有错误出口仍由 `ApiError` 输出 `{"error":{"code","message"}}`，code 全部来自 `ProtocolErrorCode`；新增 `provider_upstream_unavailable`、`provider_model_retired`、`provider_type_unsupported`、`endpoint_model_duplicate`、`endpoint_model_not_in_provider_models` 五个稳定码。所有管理面 message 改为单语 ASCII 诊断，用户文案回到客户端。

`/v1` 的所有错误出口收敛到 OpenAI 错误体。`V1Error` 统一写出 `{"error":{"type","code","param","message"}}`，`V1Json` 接管请求体解析拒绝，`/v1` 路由自带 404/405 fallback；`AppError` 不再自己拼 JSON，而是转换为 `V1Error`。`shared_quota_exhausted` 的 429 形状保持不变。

客户端只在 `errorText` 一处按码出文案；`errorReason`、`errorDetail` 和字符串子串嗅探已删除，Tauri 对所有状态先解析信封再按状态兜底。活动记录改用独立码表加可折叠诊断，供应商操作结果新增 `error_code`。

当前结论：**符合既定规则**。剩余事项都是低优先级优化或已声明的接受边界，没有阻断或重要缺口。

## 主要问题

### `/api` 体积超限仍归入 `validation_failed`

定性：建议优化。

现象：`inbound/api/error.rs` 把 `AppError::PayloadTooLarge` 映射为 `validation_failed` + 413。

风险：码与语义不完全一致，客户端只能用“请求内容不合法”解释体积问题。

建议：新增 `payload_too_large` 协议码并补客户端文案。属于独立的小变更，不影响当前契约成立。

### `/api` 方法不匹配继续用 404 表达

定性：建议优化。

现象：`inbound/api/mod.rs` 的 `method_not_allowed_fallback` 返回 `not_found`。

风险：HTTP 语义不够准确；客户端目前只有 `not_found` 文案，实际影响有限。

建议：保持现状，除非出现依赖 405 的调用方。

### 活动码新增仍依赖两端同步

定性：建议优化。

现象：服务端 `domain/activity/error_code.rs` 维护 11 个码的常量表和唯一性测试；客户端测试逐个断言这 11 个码都有文案。两端仍没有共享类型。

风险：新增活动码时，客户端测试不会感知服务端新增，界面会回退显示原始码。

建议：保持现状；活动码继续增长时再考虑生成式比对。

### 配额 DTO 的 message 仍是中文诊断

定性：建议优化。

现象：`QuotaError.message`（如“DeepSeek 余额接口返回 HTTP 429”）是中文诊断；客户端只按 `QuotaErrorCode` 出文案，不展示该字段。

风险：如果后续界面直接展示该字段，会重新引入服务端文案。

建议：保持现状并在 DTO 注释中明确“仅供诊断，不得直接展示”。

### 上游 `detail` 可能包含第三方非 ASCII 文本

定性：建议优化。

现象：`/v1` 上游失败的 message 形如 `upstream request failed: status=403 Forbidden; detail=<上游原文>`。服务端自写部分是英文，`detail` 是外部数据。

风险：上游原文可能是中文或混合语言；当前只作为诊断，不影响客户端文案。

建议：保持引用式 `detail`，不要把它拼进服务端自写的句子。

## 不纳入本次整改

- `ProtocolErrorBody.code` 保持 `String`。旧客户端能解析新码并回退到通用文案，改成枚举会破坏前向兼容。
- `http_status_for` 的既有状态映射，除新增码外不动。
- `service/upstream_errors.rs` 的截断、脱敏和 `request_id` 提取。属于安全边界，不由错误码治理顺带修改。
- 活动记录的 `error_message` 字段保留。它是审计证据，只在客户端降级为诊断详情。
- `app/utils/provider/quota/copy.ts` 的第二套映射保留。它服务配额读数域，与 API 错误码不是同一码空间。
- 不给 `/v1` 引入 `ProtocolErrorCode`。两套对外契约不同。
- `ApiError::internal` 不回传原文；只补脱敏错误类别日志。
- `/v1` 的 `detail` 继续引用上游原文，不做翻译或改写。
