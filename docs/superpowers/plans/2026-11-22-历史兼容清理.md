# 服务端历史兼容清理 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在保证 `prelay-client >= 0.3.0` 和 `/v1` 调用方正常的前提下，分批删除旧客户端 wire 兼容、旧代理死字段、Responses legacy 通道和旧供应商回退。

**Architecture:** 先清理不碰数据库的旧客户端协议面，再删除只影响旧代理的字段和列，然后分两次收口 Responses legacy，最后在数据盘点通过后处理 GoToken、旧 provider_type 和 schema 迁移基线。前三批可以独立发布；旧供应商和 schema 基线单独确认。

**Tech Stack:** Rust（`prelay-protocol`、`prelay-server`）、Nuxt/Vue/TypeScript（`prelay-client`）、Tauri、PostgreSQL、SeaORM。

**Spec:** 本计划没有独立 spec 文件；边界以 2026-11-22 对话确认的 `prelay-client >= 0.3.0` 和当前仓库事实为准。

## Global Constraints

- `prelay-client` 最低版本为 `0.3.0`；低于该版本的客户端不再兼容。
- `prelay-client v0.3.0` 连接当前服务端必须正常；当前客户端使用 `ExtensionInstallBundle.artifacts`，不再调用模型发现接口。
- 暂不放弃旧服务端兼容。`v0.3.0` 客户端连接旧服务端时使用的协议反序列化、`ExtensionSummary` 缺失字段默认值和 `/skills`、`/mcp` 回退先保留在客户端；服务端可以删除这两条过渡路由。
- `/v1` 的 Codex、Claude Code 等调用方不受 `prelay-client` 版本政策影响；`x-api-key` 和会话 header 别名继续保留。
- 旧 rollout 文件读取兼容本轮不处理。没有完成文件迁移或归档前，不删除 `ConversationFormat::Legacy`。
- 数据库测试必须使用 `TEST_POSTGRES_URL` 指向的专用测试库；不得使用生产库。
- 所有数据库删除、列删除和供应商记录删除前必须备份并执行只读盘点；未获得单独授权的破坏性动作不执行。
- 每个仓库分别提交；`prelay-protocol` 先提交，再更新 `prelay-server/crates/protocol` 和 `prelay-client/crates/protocol` 指针。
- 不推送、不打标签、不发布、不部署；这些动作分别需要用户明确授权。
- 单个 Rust 文件不超过 450 行；新增职责优先拆到独立模块，不提高 `tests/source_layout` 门禁。

## 当前事实

- 当前 `prelay-server` 为 `6ae22de`（`v0.5.4`）；执行前的基线是三个仓库工作树干净（本计划文件本身除外）。
- `/proxy` 和 `/v1/messages` 已经返回 404，`/v1` 只保留固定入口，没有通用代理 fallback。
- 生产路径中的 `ProviderConfig.token` 只被赋值为空字符串，测试夹具另有占位值；`identity_activities.proxy_token_id` 只写 `None`，两者没有读取方。
- `identity_response_sessions` 的 `legacy_internal_v1` 行不能用于 `previous_response_id`；每日清理只删除 `expires_at` 非空且已过期的行，legacy 行不会被删除。
- 新保存的每条 Responses 精确状态仍写 `input_messages_json`、`output_items_json`，但读取路径只读 `request_items_json`、`response_items_json`。
- 当前 `v0.3.0` 客户端已经使用 `/api/extensions/plugins` 和 `artifacts`；`/api/extensions/skills`、`/api/extensions/mcp` 只是旧客户端或旧服务端回退。
- 当前客户端不调用 `POST /api/providers/discover-models`。
- 生产目录已经没有 `gotoken`，但 `ProviderSpec` 回退、`target_provider_id` 映射和测试夹具仍保留 GoToken。

## 决策门

### 旧服务端兼容

默认保留旧服务端兼容，只删除服务端侧为旧客户端保留的 wire 字段和路由。若确认 `v0.3.0` 客户端也不再连接旧服务端，再删除协议 crate 的旧反序列化器和 `ExtensionSummary` 缺失字段默认值。

### GoToken 存量记录

执行前必须盘点 `identity_provider_configs` 中 `provider_type='gotoken'` 的数量及其分享、接入点模型和路由引用。

- 推荐：做一次版本化退役迁移，删除 GoToken 供应商及关联分享、接入点模型和路由，保留历史活动记录；然后删除硬编码回退。
- 保守：保留存量 GoToken 记录和回退分支，不把 GoToken 清理纳入本轮。

销毁存量供应商记录需要单独授权；未授权时只做盘点和文档记录。

### `metadata_json`

本轮不动。它和旧代理无关，且可能被多站点控制面设计引用；确认没有后续用途后再单独删除。

## 清理后的收敛性重构

这一节只处理“清理后某个字段、参数、方法或分支已经没有职责”的情况。它不是目录整理，也不是引入新抽象层。

### 准入标准

只有同时满足以下条件才进入本轮：

- 该结构只服务被删除的兼容路径，清理后没有独立职责。
- 重构以删除字段、参数、`Option`、分支或并行结构为主，不以新增 trait、service 或通用框架为主。
- 影响范围可以限制在一个职责边界内；跨调用点的机械删除不超过约十个生产文件。
- 行为不变，测试只验证收口后的契约，不为重构本身引入新的运行时行为。
- 与清理分开提交；如果字段删除是编译必需，可以放在同一逻辑单元，但在提交信息中写清楚是清理收口。

## 提交与发布顺序

每个逻辑单元独立提交，不混批次：

1. `prelay-protocol`：扩展安装包旧输出、嵌套协议字段。
2. `prelay-server`：扩展过渡路由、模型发现接口。
3. `prelay-server`：`ProviderConfig.token`、`proxy_token_id` 列。
4. `prelay-server`：Responses legacy 行清理迁移。
5. `prelay-server`：Responses legacy 列和代码删除。
6. `prelay-server`：删除 Responses legacy-only 字段。
7. `prelay-server`：GoToken 退役和旧 provider_type 收敛。
8. `prelay-server`：ProviderSpec 改为目录必传。
9. `prelay-server`：schema 迁移基线和初始化收敛。

其中 `list_by_artifact` 收口并入第 2 项，扩展安装包序列化收口并入第 1 项；Responses legacy-only 字段、ProviderSpec 和 schema 初始化分别对应第 6、8、9 项。

发布顺序：

- 先发布协议 crate 和两端 submodule 指针。
- 再发布不含数据库破坏性变更的 wire 清理。
- 然后单独发布旧代理字段和 Responses legacy 行清理，观察一个部署周期。
- 最后发布 Responses 列删除和旧供应商退役。

每次发布前重新检查目标仓库历史提交风格和当前工作树；提交、推送、打标签、发布、部署分别确认。
