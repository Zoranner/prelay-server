# 二进制安全插件安装包设计

## 目标

Prelay 必须能够按扩展仓库固定 tag 和 commit 安装完整插件包。插件包中的 PNG、图标、WASM、压缩资源及其他二进制文件与脚本、清单同等有效，不能因被错误解析为 UTF-8 文本而导致安装失败。

本设计修复当前 `assets/app-icon.png` 在插件包构建阶段被当作文本解码、再被错误映射为扩展目录 503 的根因。

## 边界

- 插件安装包包含固定版本 Git 树中所有通过既有路径安全校验的 blob 文件；目录、Git 元数据、符号链接和非法路径不进入包。
- 服务端继续是 Gitea 的唯一访问方；客户端不得直连 Gitea、保存 Gitea 凭据或接受任意仓库地址。
- Rule、Skill 和 Plugin 共用二进制安全文件传输，但只有 Rule 合并与 Skill 元数据读取要求文本语义。
- README 仍是独立的 UTF-8 文本接口，不复用安装包内容传输。
- 不按文件后缀或当前安装器引用路径裁剪插件包。资源是否被插件运行时使用，由插件自身定义。

## 协议

`prelay-protocol` 中的 `ExtensionFile` 改为：

```text
path: String
content_base64: String
```

`content_base64` 是原始文件字节的标准 Base64 编码。该字段在服务端、客户端和协议测试中统一使用；不保留字符串内容字段或双格式兼容入口。

规则和 Skill 在客户端安装前解码字节，并在各自需要文本的位置执行 UTF-8 校验。插件安装器只解码并原样写入字节。这样同一个安装包可以同时包含插件清单、脚本和二进制资源。

## 服务端

Gitea 文件读取层返回原始 `Vec<u8>`，不在读取层执行 UTF-8 解码。扩展目录构建器将每个安全 blob 的字节编码为 `content_base64` 后写入 `ExtensionInstallBundle`。

插件分支枚举该版本的完整安全 blob 集合。Rule 与 MCP 仅枚举其固定入口文件；Skill 枚举 `skills/` 下的完整安全文件集。README 在独立读取路径中解码为 UTF-8。

Gitea 请求失败仍为 `extension_catalog_unavailable` 和 HTTP 503。Gitea 返回的内容无法 Base64 解码、Rule 或 Skill 的必需文本不是 UTF-8、或安装包违反路径约束时，返回新的稳定错误码 `extension_content_invalid` 和 HTTP 422；这些不是目录可用性故障。

## 客户端

客户端为扩展文件提供唯一的 Base64 解码入口。该入口拒绝无效编码，并将解码后的原始字节交给目标安装器。

- Rule：解码后要求 UTF-8，再合并到目标 `AGENTS.md`。
- Skill：解码后原样写入 `skills/`；只有解析 `SKILL.md` 的既有流程自行要求 UTF-8。
- Plugin：解码后将所有包内文件原样写入 Codex 或 OpenCode 的插件缓存。PNG 等资源必须与仓库固定版本字节一致。

本地磁盘失败仍返回 `local_extensions_error`，与服务端安装包错误保持区分。

## 验证

- 协议测试验证 Base64 字段序列化和反序列化，不允许旧文本字段。
- 服务端目录测试使用插件清单、脚本和 PNG 字节 fixture，断言安装包保留完整文件集合与原始字节。
- 客户端扩展测试解码包含 PNG 的插件包，断言落盘文件逐字节一致；Rule 的非 UTF-8 内容必须被拒绝。
- 管理路由测试区分 Gitea 不可用的 503 与内容无效的 422。

## 非目标

- 不改变扩展仓库发现、分类、tag 选择或客户端的本地安装目标。
- 不增加客户端直连、上传扩展或运行时下载路径。
- 不为旧版字符串安装包保留兼容解析。
