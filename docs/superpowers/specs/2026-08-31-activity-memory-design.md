# 活动与自动记忆设计

## 目标

为 Prelay 增加基于活动正文的自动记忆能力。记忆只面向当前服务实例所属团队共享，不引入会话、消息或人工上传文档等新概念。每条记忆都能标识贡献它的 `identity_id`，并保留足以解释和纠错的脱敏证据。

本阶段的设计目标是确定领域边界、持久化职责、自动处理流程和后续扩展方向，不包含实现、协议发布或前端页面改造。

## 非目标

- 不建设审计系统，不承诺永久保存完整活动正文。
- 不把活动改造成配额、计费或限流数据源。
- 不引入会话、消息、人员账号或独立团队管理实体。
- 不要求外部消息队列。
- 不保存 Provider API Key、Endpoint Token、设备凭据或请求头。

## 领域概念

### 活动

活动表示一次服务调用及其运行结果。活动包含当前系统已经记录的身份、接入点、协议、模型、状态、用量、耗时和错误等信息。客户端的“活动”页面和统计视图都从活动数据读取；统计只是活动的聚合查询。

现有实现中的 `request_logs`、`RequestLogInsert`、`RequestLogSummary` 等名称属于历史实现命名，后续领域模型统一使用 `activity` 语义。

### 活动正文

活动正文是活动中用于自动提炼的规范化文本快照，包含必要的输入文本和输出文本。它不是会话或消息记录，也不要求理解客户端如何组织上下文。

活动正文与活动运行字段分开保存，避免活动列表和统计查询被大文本拖慢。正文可独立设置大小限制、脱敏策略、处理状态和保留期限。

### 记忆

记忆是团队可共享、可检索、可持续修正的结构化知识单元。第一阶段以事实、偏好、规则和实体描述为主，允许保留关系字段，为后续图关系检索提供基础。

记忆至少包含：

- 规范化内容；
- 类型和状态；
- 置信度；
- 创建和更新时间；
- 一个或多个记忆来源。

### 记忆实体与关系

记忆实体和关系是从记忆正文中提炼出的结构化事实，不是由相似度或
`conflict_key` 反推的装饰性图谱。实体名称、实体类型和关系谓词都使用开放
字符串，不建立预先限定的分类枚举。

实体用于表示可复用的对象、概念或值；关系用于表达某条记忆所断言的主体、
谓词和客体。关系必须关联其断言记忆，因此可以经由记忆和记忆来源追溯到
`identity_id`、脱敏证据和观察时间。实体本身不复制贡献者或证据。

### 记忆来源

记忆来源说明一条记忆由谁贡献、何时形成以及依据是什么。来源只保存 `identity_id`、脱敏证据和时间，不强制绑定活动 ID。自动提炼模型是处理者，不是贡献者。

一条记忆可以关联多个来源，多个身份可以共同贡献同一条记忆。合并、冲突和修正都不能丢失已有来源。

## 数据职责

逻辑模型分为八类数据：

```text
activities
  运行记录和统计所需字段

activity_contents
  活动正文、脱敏结果和处理状态

memories
  团队共享的规范化记忆

memory_sources
  记忆与 identity_id、证据和时间的关联

memory_entities
  规范化实体及其开放类型

memory_entity_mentions
  记忆与实体的提及关系

memory_relations
  记忆断言的主体、谓词和客体

memory_projection_jobs
  目标、upsert/delete 操作、对象版本、状态、租约和重试信息
```

`activities` 是运行观测数据，`activity_contents` 是可选内容数据，`memories`、
`memory_sources`、`memory_entities`、`memory_entity_mentions` 和
`memory_relations` 是长期的结构化记忆事实，`memory_projection_jobs` 是派生
投影的处理状态。外部索引不替代这些 SQL 表。

## 活动正文采集

活动完成后，在不影响响应的前提下提取正文：

1. 从各协议桥接层取得规范化输入文本和输出文本。
2. 删除凭据、密钥、授权头和其他敏感字段。
3. 对图片、截图和二进制内容只保留类型、大小、哈希或已获得的文字提取结果。
4. 按字节数限制正文；超过限制的内容截断并记录截断状态。
5. 将正文写入 `activity_contents`，状态标记为待处理。

完整原始 JSON、请求头和附件内容不进入活动正文。活动正文保存失败不能影响已经成功的活动响应，也不能覆盖活动的运行状态。

## 自动提炼流程

```text
活动完成
  -> 规范化和脱敏正文
  -> 写入活动正文
  -> 后台领取待处理正文
  -> 提取事实、实体、偏好和关系候选
  -> 规范化、去重、合并和冲突判断
  -> 写入记忆、来源、实体和关系
  -> 创建或更新图与向量投影任务
  -> 标记正文处理完成
```

后台处理是慢路径，不阻塞正常上游调用。处理失败保留可重试状态、次数、下一次处理时间和脱敏后的错误原因。处理必须幂等：同一正文重复领取或服务重启后重试，不能重复创建等价记忆或重复来源。

提炼模型通过现有 Provider/Endpoint 配置调用，不在记忆模块中写死具体供应商。提炼请求和普通业务活动使用相同的密钥保护、超时和错误边界，但提炼失败不能影响原始活动结果。

实体和关系候选与记忆候选在同一 SQL 事务内持久化。每条关系关联一个
`memory_id`；同一记忆的多个来源因此天然适用于其所有关系。关系更新、记忆
状态变更或删除会创建相应的投影更新或删除任务，不能只修改 FalkorDB。

## 记忆规范化与冲突

候选记忆写入长期数据前执行以下步骤：

- 规范化实体名称、别名和事实表达；
- 用稳定的规范化键进行精确去重；
- 对无法精确匹配的候选保留待判断状态，不用相似度直接覆盖已有事实；
- 新旧事实冲突时保留双方来源和时间，由状态表示当前、过期或存在冲突；
- 删除或归档记忆时保留来源关系，避免无法解释历史结果。

第一阶段不自动把低置信度候选提升为高置信度事实，也不因为单次活动中的推测性回答生成长期规则。

## 检索设计

记忆检索按以下顺序演进：

1. SQL 的结构化字段、关键词和时间过滤；
2. FalkorDB 的向量召回，并由 SQL 重新读取记忆状态和来源；
3. 以召回记忆关联的实体为起点，在 FalkorDB 进行有限深度的关系扩展；
4. 对候选结果执行来源、状态和时间过滤后返回。

FalkorDB 是图与向量一体化的外部检索投影，不保存权威来源证据、
`identity_id`、活动正文或完整记忆正文。投影节点和边只保留稳定 SQL ID、
版本、开放类型、规范化显示属性、状态、必要的时间字段和向量。向量命中和
图遍历结果必须回到 SQL 校验，避免过期投影泄漏已删除或已归档的记忆。

图形结构固定为：

```text
(:Memory {memory_id, revision, kind, status, embedding})
  -[:MENTIONS]->
(:Entity {entity_id, normalized_key, name, entity_type})

(:Entity)-[:RELATES {
  relation_id, memory_id, predicate, status, confidence, observed_at
}]->(:Entity)
```

关系边只表达一条记忆断言，不因多个来源而合并或覆盖。图谱展示和关系详情
经由 `memory_id` 回查 SQL 的记忆与来源，以保留冲突、证据和贡献者解释。

团队记忆默认对当前服务实例内已认证的管理身份可见。访问控制沿用现有身份和管理 API 边界；贡献者信息只从 `identity_id` 关联身份数据得到，不在记忆中复制凭据或秘密。

## 生命周期与保留

- 活动运行字段按现有活动保留策略管理。
- 活动正文是自动提炼的中间输入，可以比活动元数据更短地保留。
- 记忆是长期数据，除非被明确删除、过期或冲突归档，否则不随活动正文清理而删除。
- 记忆保留最小脱敏证据；清理活动正文不应破坏已有记忆的来源说明。
- 正文大小、保留期限和是否启用自动记忆属于服务端部署配置，不由单次请求控制。

## 数据库与部署

Prelay 继续支持独立选择 SQLite 或 PostgreSQL 部署，不做跨数据库迁移。核心表和状态字段使用 SeaORM 可表达的公共能力。FalkorDB 通过独立连接配置为可选服务，不改变 SQLite/PostgreSQL 的真相源边界，也不要求两种 SQL 部署使用不同领域模型。

FalkorDB 每个 Prelay 服务实例使用一个固定的逻辑图。连接配置缺失时，服务端不尝试连接 FalkorDB，记忆读取降级为 SQL 的结构化和关键词检索；原始活动、正文保存和记忆提炼继续工作。启用后，FalkorDB 不可用只会使投影任务进入可重试失败，不能阻塞活动响应、记忆写入或 SQL 检索。

`memory_projection_jobs` 以目标、操作、对象类型、对象 ID 和版本保证幂等。worker 使用已有的状态、租约、尝试次数、下次处理时间和脱敏错误边界领取任务；对同一版本的重复投递必须得到相同的 FalkorDB 节点、边或删除结果。全量重建先清空指定逻辑图，再从 SQL 枚举当前记忆、实体和关系并重新创建投影任务。重建过程不读取已经到期删除的活动正文。

第一阶段不增加外部队列。待处理正文通过数据库状态和租约字段领取，允许单实例运行，也为后续多实例扩展保留幂等和重试边界。只有当数据库 worker 无法满足吞吐或故障恢复要求时，才评估引入队列。

## 阶段划分

### 阶段一：活动正文和自动提炼

- 将历史实现命名统一到活动语义；
- 增加活动正文的脱敏、大小限制和保留策略；
- 增加待处理状态和后台提炼 worker；
- 持久化记忆、来源、置信度和冲突状态；
- 提供最小的团队记忆读取能力。

### 阶段二：关系事实与 FalkorDB 投影

- 增加实体、记忆提及和关系断言的 SQL 模型；
- 增加 FalkorDB 图和向量投影适配层；
- 增加投影任务的幂等、重试、删除和全量重建；
- 支持向量召回后有限深度的关系扩展。

### 阶段三：检索质量

- 采集提炼质量和召回评测数据；
- 支持按时间、来源身份和记忆状态筛选；
- 支持多来源冲突可视化和修正；
- 在真实查询规模证明确有必要时，调整 FalkorDB 索引参数或评估专用扩展。

## 验收标准

- 设计和实现中不出现会话、消息作为持久化领域实体；
- 客户端和服务端统一使用“活动”命名；
- 每条记忆可以查询贡献它的 `identity_id` 和脱敏证据；
- 活动响应不依赖记忆提炼成功；
- 正文重复处理不会产生重复记忆；
- 活动元数据、活动正文和记忆可以分别清理；
- SQLite 和 PostgreSQL 都能使用同一核心数据模型；
- 任何索引损坏或删除都可以从核心表重建。
- FalkorDB 不可用或未配置时，活动和记忆主链路保持可用；
- 图关系可以经由关系断言、记忆来源回查到 `identity_id`、脱敏证据和时间；
- 图与向量投影不保存活动正文、来源证据或身份标识。

## 当前明确不做的决定

- 不建立人员账号映射；当前贡献者粒度就是已有 `identity_id`。
- 不把活动 ID作为记忆来源的强制字段。
- 不保存完整原始请求、响应、图片或截图作为长期记忆数据。
- 不为自动记忆增加手动上传、手动 remember 或独立文档库入口。
- 不在本阶段改动公开 `/v1` 协议；记忆能力先作为服务端内部能力设计。
- 不把 FalkorDB 当作活动、正文、记忆、实体、关系或来源的真相源。
