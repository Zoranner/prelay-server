# 扩展必装与弃用策略设计

## 背景

当前扩展目录按 Gitea 组织下的仓库、标签和文件树生成。客户端只在用户安装或更新时读取目录，本地安装状态不会因为服务端删包、改名或下架而变化。

这带来两个问题：

- 服务端不再提供某个包时，本地安装继续保持原状，用户无法从目录中发现它已经失效。
- 旧包改名后，新包如果声明相同的 Skill、MCP 或 Hook 制品，安装预检会把它判定为另一个插件占用了目标，新包无法安装。

扩展包本身没有可写的清单文件，策略不适合再引入仓库内 JSON。采用 Gitea topic 作为唯一策略来源：`required` 表示必装，`deprecated` 表示弃用。仓库名和包名保持不变，策略不改变安装身份。

## 目标

- 服务端读取 Gitea topics，并把插件包策略传给客户端。
- `required` 插件由客户端自动安装和更新；本地缺失时安装，版本落后时更新。
- `deprecated` 插件由客户端自动卸载本地同名插件；不要求知道后继包，用户自行安装新包。
- 自动操作不覆盖未受管的个人 Skill、MCP 或 Hook；冲突、只读和未完成状态保留现状并报错。
- 旧客户端连接新服务端、新客户端连接旧服务端时，不产生协议反序列化失败或误装。
- 包名保持稳定，策略变化不修改本地安装记录的文件名。

## 非目标

- 不支持规则包的自动安装或自动卸载。规则包仍按现有规则编辑器处理。
- 不建立旧包到新包的映射，也不要求 `deprecated` 包声明后继包。
- 不恢复仓库名后缀约定；不使用 `+`、`-` 或点前缀表达策略。
- 不新增绕过 Codex Hook 信任的路径。沿用现有安装时的自动信任写入；写入失败时保留警告，由用户在 Codex 中手动批准。
- 不新增服务端管理页面、数据库表或独立策略服务；topic 由 Gitea 维护。
- 不改变版本标签、安装包结构、制品类型和现有安装/卸载语义。
- 不做秒级轮询；沿用客户端启动检查、现有 30 分钟后台检查和手动刷新。

## 术语

**策略**：插件包的生命周期标记，取 `normal`、`required`、`deprecated`。

**必装包**：带 `required` topic 的插件包。客户端在成功读取目录后自动补齐或更新。

**弃用包**：带 `deprecated` topic 的插件包。客户端在成功读取目录后自动卸载本地同名插件。

**策略同步**：一次完整读取插件目录，并按顺序执行卸载与安装的过程。同步失败时不执行任何自动动作。

**宿主**：本地安装域。当前只有 `codex`，Codex CLI 与 ChatGPT 共用同一宿主状态。

## 策略来源

Gitea topic 只接受两个保留值：

```text
required
deprecated
```

- topic 按小写精确匹配，其他 topic 忽略。
- 同一仓库同时带两个 topic 视为策略冲突：如果最终分类为插件，服务端记录仓库名并跳过该包，不写入插件目录，客户端不对它执行自动动作；规则包仍忽略策略。
- topic 读取失败时，整次目录刷新失败并保留上一份成功快照；不能把未知策略当作 `normal`。
- 规则包上的策略 topic 不生效。服务端仍按规则包处理并记录警告。
- 弃用仓库必须保留至少一个有效发布标签和可分类的文件树，直到客户端完成清理。没有有效版本的弃用仓库无法确认是否为插件，服务端跳过并记录警告。

服务端通过以下 Gitea API 读取 topic：

```text
GET /api/v1/repos/{organization}/{repository}/topics
```

响应中的 `topics` 数组用于计算策略。请求使用现有 `EXTENSIONS_GITEA_READ_TOKEN`，权限要求与读取标签、文件树相同。每个仓库通常增加一次 topic 请求；单页 50 条、超过时逐页读取并去重，最多 10 页。当前目录扫描已经逐仓库请求标签和文件树，缓存仍按现有 TTL 生效。

## 协议

`prelay-protocol` 增加策略枚举：

```rust
pub enum ExtensionPolicy {
    Normal,
    Required,
    Deprecated,
}
```

- 序列化为小写字符串。
- 缺少字段或未知值按 `normal` 处理，保证新服务端增加策略值时旧客户端仍能读取目录。
- `ExtensionSummary` 增加 `policy` 字段，默认 `normal`。
- `/api/extensions/plugins` 仍然只有一条列表、一个响应，普通、必装和弃用三类插件包都出现在里面，每项用 `policy` 区分；不新增独立接口。
- 弃用包保留在列表响应中作为清理信号，但服务端拒绝它的版本、README 和安装包请求，旧客户端即使看到条目也无法继续安装。
- `/api/extensions/rules` 的条目恒为 `normal`；规则包不参与策略。

协议不新增接口、不新增 DTO、也不新增错误码。弃用状态只由 `policy` 表达；针对弃用包的版本、README 和安装请求返回现有的 `extension_not_found`。

客户端展示模型 `ExtensionPackage` 增加 `policy`，默认 `normal`；安装请求不接收客户端提交的策略，策略只由服务端目录决定。

## 服务端

`GiteaClient` 增加 `topics(repository)` 方法，返回 `Vec<String>`。目录扫描在读取标签前获取 topic，并把策略结果与目录快照一起缓存。

扫描规则：

| 仓库情况 | 处理 |
| --- | --- |
| 无策略 topic，内容有效 | 按现有规则加入规则或插件目录，策略为 `normal` |
| `required`，内容有效且是插件 | 加入插件目录，策略为 `required` |
| `deprecated`，内容有效且是插件 | 加入插件目录，策略为 `deprecated` |
| `required`，没有有效版本 | 跳过并记录警告；不中断目录刷新 |
| `required`，有有效版本但内容无效 | 整次刷新失败，保留上一份快照 |
| `deprecated`，没有有效版本或内容无效 | 跳过并记录警告；客户端收不到弃用信号 |
| 同时有 `required` 和 `deprecated`，且分类为插件 | 跳过并记录警告 |
| 策略 topic 出现在规则包 | 忽略策略，仍按规则包处理 |
| topic 请求失败 | 整次刷新失败，保留上一份快照 |

必装包的目录校验只读取 `server.json`、`hooks/hooks.json` 和各 `SKILL.md`；完整安装包仍在安装时校验。topic 按 50 条分页读取并去重，最多 10 页。

`ExtensionCatalog` 只保留一份目录缓存，策略随条目一起保存，不再维护第二份列表。`list` 按 `CatalogKind` 返回该分类下的全部包，包括 `deprecated`。`entry` 只接受 `normal` 和 `required`，因此弃用包的版本、README 和安装请求都返回不存在。

服务端在策略新增、移除或变化时记录带仓库名和策略的 info 日志，不记录 token、请求头或安装包内容。topic 的写权限由 Gitea 仓库管理权限约束。

## 冲突判定

手动安装、手动更新、`extensions_update_all` 和策略同步的自动安装共用这一套判定。归属只看 `~/.prelay/hosts/<host>/plugins/<name>.json`，不看宿主内容。

| 目标现状 | 判定 | 安装或更新行为 |
| --- | --- | --- |
| 记录声明给本包 | 受管 | 直接覆盖或更新，不校验内容 |
| 记录声明给其他包 | 归属冲突 | 中止并返回 `local_extensions_conflict`，`overwrite` 不越过 |
| 有宿主内容、没有任何记录声明 | 未受管 | 返回 `extension_target_exists`；手动安装确认后可用 `overwrite=true` 覆盖，自动安装直接记录失败 |
| 宿主没有对应内容 | 空闲 | 直接安装 |

- 两个错误码分工固定：`local_extensions_conflict` 只表示归属不在本包，不提供覆盖确认；`extension_target_exists` 只表示未受管内容占用，可经用户确认覆盖。
- 手动安装和手动更新收到 `extension_target_exists` 时弹确认，确认后以 `overwrite=true` 重试；收到 `local_extensions_conflict` 只提示先卸载占用方，不弹覆盖确认。
- 自动安装不弹确认，按上表直接记录失败，下一轮同步重试。
- `overwrite=true` 只越过未受管内容，不越过其他插件的声明，也不越过只读状态和既有重复声明冲突。
- 宿主内容只回答“在不在”：用来识别未受管内容、发现缺失的受管制品。它不判断归属，也不判断受管制品是否被修改；界面的“缺失/被修改”仍按现有健康检查展示，但不阻断安装或更新。
- 更新不再对本包已管理的制品做内容校验：MCP 的 `manifestHash`、Skill 内容和 Hook 哈希都不参与冲突判定。新版本不再声明的旧制品也直接删除，不再因为被改过而中止。

## 客户端

`list_extensions` 继续负责读取目录和计算安装状态。服务端返回的 `policy` 原样放入 `ExtensionPackage`；缺少字段时按 `normal` 处理。推给界面的目录快照不包含 `deprecated` 包，避免出现可安装条目。

新增策略同步模块，职责是读取插件目录并按宿主状态执行自动卸载和安装。它直接消费协议层的列表响应，和 `list_extensions` 共用同一个目录接口与服务端缓存；不放在 `list_extensions` 内部，避免读目录接口产生删除副作用。

### 触发

- 客户端启动后，在 relay 地址可用且身份注册可用时执行一次。
- 现有后台扩展检查每次成功读取插件目录后执行一次。
- 扩展页手动刷新时执行一次，然后重新读取目录。
- 同一进程只允许一个策略同步运行；后台检查和手动刷新同时触发时复用或等待同一个同步。

### 顺序

先处理 `deprecated`，再处理 `required`，同一组按包名排序。

先卸载可以为必装包释放 Skill、MCP 和 Hook 目标。必装包如果仍与个人内容或其他插件冲突，安装失败并保留现状，不自动使用 `overwrite`。

### 弃用卸载

- 只处理本地存在同名插件状态的情况；不存在时跳过。弃用卸载按宿主状态执行，不依赖当前是否检测到 Codex CLI 或 ChatGPT。
- `installed` 状态执行现有卸载流程，清理该宿主的 Skill、MCP、Hook 和插件状态。
- `removing` 状态允许重试卸载；`installing`、只读状态和归属冲突记录错误并跳过，不强制删除。
- 记录声明给本包的制品按记录直接删除，不再比对 MCP 配置是否被改过；这与更新时直接覆盖保持一致，也避免弃用包因为用户改动过就永远删不掉。
- 现有卸载流程不校验 Skill 文件内容；用户手工修改过的 Skill 目录仍会随卸载删除。需要保留这类修改时，应先执行手动卸载或先取消 topic。

### 必装安装

- 本地没有记录：安装目录中的最新固定版本。
- 记录版本或 commit 落后：更新到最新版本。
- 版本一致且声明的制品都存在：跳过。
- 版本一致但有受管制品不存在：按记录补装一次。
- `installing`、`removing` 或受管制品缺失：重试一次；内容被改过但身份仍在时按 `up-to-date` 跳过。
- 制品“存在”按身份判断：Skill 看目标目录，MCP 看 `config.toml` 服务名，Hook 看 handler 哈希。内容被改过但身份仍在，不触发重装。
- 没有检测到可用客户端：跳过并记录待安装原因，下次同步重试。
- 只安装到已检测且支持该包制品的客户端。当前 Codex CLI 与 ChatGPT 共用 `codex` 宿主，只写入一份宿主状态。
- 安装使用 `overwrite=false`，冲突按“冲突判定”一节处理：未受管内容占用记录失败，归属冲突同样记录失败，都不重试覆盖。
- 记录声明给本包的制品视为受管，更新时直接按新包内容重写，不比对 Skill 内容、MCP `manifestHash` 或 Hook 哈希；用户对这些受管制品的修改会被覆盖。
- 安装结果包含 Hook 信任警告时保留警告；沿用现有安装时的自动信任写入，不新增绕过信任的路径。

必装包被用户从智能体页手动卸载后，本地状态消失；下一次策略同步会重新安装。本期不在智能体页拦截卸载动作。

### 失败与恢复

- 插件目录读取失败时，整次策略同步不执行自动安装或卸载，保留本地状态。
- 单个包失败不阻断其他包；同步返回逐包结果，下一次同步重试。
- 安装或卸载中断后沿用现有 `installing`、`removing` 和 `partial` 语义，不自动修复无法确认的宿主内容。
- 同步不产生无限重试；失败结果在下一轮启动、后台检查或手动刷新时重新评估。

### 结果与界面

同步返回结构至少包含：

- 已卸载的包名。
- 已安装或更新的包名。
- 跳过的包名和原因。
- 失败项的错误码与消息。
- Hook 信任警告、需要审核的 Hook 条目或其他警告。

后台同步完成后推送 `extensions:policy` 事件，前端刷新插件目录并展示结果。扩展目录只显示可安装包；必装包显示“必装”标记，不显示 topic 名。弃用包由原生层从展示快照中过滤，前端不提供安装入口。失败项通过通知或扩展页状态呈现，并提供手动刷新重试。

## 安全边界

`required` 会让服务端向所有客户端下发 Skill、MCP 和 Hook 配置，等同于远程下发可执行内容；`deprecated` 会删除本地受管内容。Gitea 组织必须限制仓库和 topic 的写权限，只允许受信任的管理员操作。

服务端只从 Gitea topic 读取策略，不接受客户端提交的策略覆盖。客户端不缓存策略作为独立的长期事实，每次以成功读取的服务端快照为准。

部署方必须确认行为符合预期后再设置 `required`。服务端日志应能定位仓库名和策略，但不能记录 token、凭据、请求头或安装包内容。

## 兼容与发布

- `ExtensionSummary.policy` 缺失时按 `normal` 处理；旧客户端忽略该字段。
- 旧客户端会在插件列表里看到弃用包，但服务端拒绝其版本和安装包请求，只保留条目、无法安装；旧客户端本地已有安装不会自动卸载。
- 新客户端连接旧服务端时，`policy` 缺失视为 `normal`，不执行任何自动动作；无需为独立接口做 404 兜底。
- 新服务端连接旧客户端时，必装包按普通包展示和手动安装，弃用包可显示但不可安装；不会产生反序列化失败或误装。
- 先发布协议和服务端，再发布客户端；确认目标客户端已经具备策略同步能力后，再给仓库设置 `required` 或 `deprecated`。
- 本地状态文件名和插件名不变，不需要迁移。旧包改名场景应保留旧仓库名并设置 `deprecated` topic，等客户端清理后再处理旧仓库。
- 冲突判定统一属于客户端行为变更，不改服务端接口：旧客户端收到 `local_extensions_conflict` 只会报错，不再弹覆盖确认；规则目标被其他包占用后也不再允许靠 `overwrite` 抢占。

## 运维约定

- 弃用包必须保留原仓库名、至少一个有效发布标签和可分类内容，直到所有客户端完成清理。直接删除仓库或直接改名不会产生弃用信号。
- 规则包不要设置策略 topic；设置了也不会生效。
- 必装包不应与个人内容或其他必装包声明相同的 Skill、MCP 服务名或 Hook；否则客户端会报冲突，不会覆盖。
- 必装包包含 Hook 时，用户仍需在 Codex 中完成信任审核。
- 同一仓库不能同时保留 `required` 和 `deprecated`。

## 验证

协议仓：

- `policy` 缺省、未知值、正常序列化和反序列化。
- 三种策略经 `ExtensionSummary` 序列化后仍能被旧结构反序列化，未知字段被忽略。

服务端：

- mock Gitea 目录为每个仓库提供 topics 路由，覆盖 `required`、`deprecated`、双 topic、无 topic 和规则包 topic。
- 弃用包出现在 `/extensions/plugins`，`policy` 为 `deprecated`；必装包为 `required`。
- 弃用包的版本、README 和安装请求返回 `extension_not_found`，与它是否出现在列表无关。
- `/extensions/rules` 的条目恒为 `normal`。
- topic 请求失败、必装包内容无效或没有有效版本时，整次刷新失败并保留旧快照。
- 目录缓存只保存一份列表，刷新失败不清空旧结果。

客户端：

- 成功同步时先卸载弃用包，再安装缺失的必装包，再更新落后版本的必装包。
- 同版本必装包、没有检测到客户端、弃用包不在本地时正确跳过。
- 目录读取失败时不执行自动安装或卸载。
- 手动安装、手动更新和自动安装对同一目标给出一致的判定：本包记录可覆盖，其他包记录返回 `local_extensions_conflict`，未受管内容返回 `extension_target_exists`。
- 手动安装收到 `extension_target_exists` 后确认并以 `overwrite=true` 重试成功；收到 `local_extensions_conflict` 时不弹确认，`overwrite=true` 仍然失败。
- 规则目标由其他包管理时，`overwrite=true` 不再生效，返回 `local_extensions_conflict`。
- 自动安装遇到归属冲突或未受管内容时记录失败，不覆盖、不重试覆盖。
- 记录声明给本包的 MCP 被用户改过时，更新直接按新包重写，不报冲突；Skill 目录被删除时按缺失重新安装。
- 记录声明给本包的 MCP 被用户改过后仍能正常卸载。
- Hook 信任警告进入同步结果。
- 连续启动、后台检查和手动刷新不会并发写入，重复同步幂等。
